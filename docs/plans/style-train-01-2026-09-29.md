# STYLE-TRAIN-01: train and convert one adapter per companion

## Why

`STYLE-CORPUS-02` (landed `084c3140`) built the class-aware training data
generator: `backend/scripts/voice/corpus.ts` produces, per companion, a
JSONL of (neutral reply, companion-voice rewrite) pairs, each recording
its own class/shape and the exact system prompt its neutral reply was
generated under. This item trains the actual adapter files from that
data - the first of the four companion voices to genuinely exist as a
trained artifact, not a design record.

Read `VOICE-CLASS-01`'s design pass and `STYLE-CORPUS-01b`/
`STYLE-CORPUS-02`'s closed rows in `docs/dev.md` before starting - they
explain why a document-shaped row's body trains at near-zero loss by
design (it's the base model's own text, copied verbatim) and why the
real learning signal sits in the frame and spoken rows specifically.
Report the share of rows per class/shape in your own run report, per
the row's own dated note.

## Hardware and environment - read this before anything else

This needs a real GPU (the tier-2 bench laptop, `maipai-home` at
`172.19.210.52`, or the Studio once it's here - the laptop is what
exists right now). Unlike the corpus generator (pure inference against
an already-running llama-server), this is a **training** job: PEFT with
TRL's SFT trainer, a Hugging Face `Qwen/Qwen3-8B` base, 4-bit
quantization. That's a Python ML stack (`transformers`, `peft`, `trl`,
`bitsandbytes`, a CUDA-matched `torch`) that has **not been verified to
exist** on this laptop - the existing setup there is the C++ llama.cpp
inference stack, a different toolchain entirely. Check what's actually
installed (`ssh -i ~/.ssh/id_maipai_laptop maipai-admin@172.19.210.52`,
per the four NOPASSWD sudo commands already granted there for the wake/
reboot cycle - installing Python packages is not one of those four, so
if `sudo` is needed for anything beyond those four commands, stop and
ask the coordinator rather than working around the grant) before writing
a line of `train.sh`. If the stack needs installing, that installation
is real, in-scope setup work for this item, not a blocker to report and
stop on - but if it needs anything beyond user-level `pip`/`uv` (a
system package, a driver change, disk space you can't free yourself),
stop and ask.

This training job likely only needs the laptop's **internal** RTX 2070
Super (8 GB, matches "4-bit base on an 8 GB card"), not the eGPU - the
eGPU's flaky-Thunderbolt-link history (documented in the separate
homelab repo, referenced for context, never edited by this item) is a
real risk you can likely avoid entirely by not touching it. Only reach
for the eGPU if the internal card's 8 GB genuinely isn't enough once you
try; if so, stop and ask the coordinator before attempting any eGPU wake
cycle yourself.

## Steps

1. Verify the Python ML stack on the laptop per "Hardware and
   environment" above. Install what's missing at user level if you can;
   stop and ask if you can't.
2. Generate (or confirm already exists) the real, full-scale corpus per
   companion via `backend/scripts/voice/corpus.ts` against the local
   27B teacher (`MAIPAI_VOICE_TEACHER_URL=http://172.19.210.52:8791`) -
   `STYLE-CORPUS-01b`/`02`'s own runs were all at reduced scale
   (n=35-45 typed/15 spoken) to keep review cycles fast; this item needs
   the real training set, so run at the row's own default scale (about
   400 typed, 200 spoken) unless time makes that genuinely impractical,
   in which case report exactly what scale you trained on and why, the
   same honesty the corpus items already established - never pad or
   imply a larger set than what was actually used.
3. Write `train.sh` and `train.md` per the row's exact parameters. Cite
   your sources for anything you decide beyond what the row already
   specifies (library versions, exact flags) directly in `train.md`.
4. Train all four adapters in the stated order, then convert each with
   llama.cpp's `convert_lora_to_gguf.py` at the pinned tag `b10797`
   (matching the tag already used elsewhere in this codebase - confirm
   it, don't assume a different version is fine).
5. Verify each adapter actually loads: start a throwaway llama-server
   instance (not the laptop's live `maipai-chat` unit - a separate,
   temporary one you start and stop yourself, on a port that doesn't
   collide) with `--lora <file>`, confirm `GET /lora-adapters` lists it,
   and stop that instance cleanly when done. Never touch or restart the
   laptop's live production units.
6. Record each adapter's sha256, size, the training loss curve's final
   value, and wall time in `dev.md`, plus the per-class/shape row-share
   your run actually used (per "Why" above).
