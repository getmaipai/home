Both already decided that an app page is a `page` document through the existing SchemaPage and NodeRenderer path, that its route

## The smallest design, in one paragraph

An app is an installed package whose manifest lists schema pages. Three read-only routes expose it (the app list, one page
document, one data call). The frontend gets one wildcard route and one merged catalog hook, so install and uninstall change what
the library, search, pins and the rail see with no rebuild. The page runs through today's interpreter plus three additive pieces:
a package-scoped binding guard, one node that draws answer blocks, and one node that picks a value into page state. Weather's
hero is the kit Element the existing weather answer block already maps to. No new record type, no new store, no new outbound call.

## What is missing (and the smallest addition for each)

1. **A package page must not reach outside its package.** Today `useBinding` calls `request(binding.path)` with any path, and a
   `call` action takes any `target`. A package page could read `/api/people` or `DELETE` a record. Add `PackageScopeContext` (set by
   the shell when it mounts a package page) and one rule in the interpreter: inside that context a binding and a `call` target are
   resolved only under `/api/plugins/<that id>/` (see "Binding" below) and `navigate.to` only under `/apps/<that id>/`. Anything
   else renders an `empty_state` and logs one typed `app.page_rejected` event with no path text. This is the existing backlog
   item's guard, unchanged in intent.
2. **A binding that carries inputs.** Today bindings are a bare GET. Weather needs the chosen place, and Current location is
   coordinates that must never ride a URL. Add `source: "package"` (additive enum value) and optional `params` on the binding: a
   map of literal values or `$state.<name>` references. The interpreter sends a package binding as `POST` with `params` as the JSON
   body. Query key is `[package, data id, params without coordinates, nonce]`; the nonce changes when the person re-shares their
   location.
3. **A node that draws answer blocks.** `widget_card` renders `{items}` text only. Add `answer_blocks`:
   `{type, bind, kinds?, empty_state?}`. It validates each block with the existing checker and hands it to the existing
   `answer-block.tsx` dispatch (rule 9: the one small checker, all drawing in the kit). `kinds` lets a page place one kind per
   section; the Weather app page draws the `weather_card` block as its hero. A block kind the client does not know falls back to its `alt`
   sentence, which is also what the robot says.
4. **A node that writes page state.** Add `picker`: `{type, state, bind, item_key_field, item_label_field, leading[]}` where
   `leading` is a list of fixed options (`value`, `label`, `icon`, optional `needs: "geolocation"`). Choosing an option writes
   `state.<name>`; an option with `needs: "geolocation"` asks the browser only on that tap and keeps the coordinates in memory.
   The existing `condition` evaluator already reads page state, so `section.condition` can hide the empty state or show a
   permission-denied line. The picker renders the kit's select primitive; Home adds no markup.
5. **A data declaration in the manifest.** `contributes.widgets[]` is card-sized text. Add `contributes.data[]`:
   `{id, surface?, inputs?, refresh_s?}`; `surface` names a `resolvePlace` surface (`weather` or `maps`) so the host, never the
   model or the page, injects resolved latitude and longitude into the recipe call (the PLACE-WEATHER-01 mechanism). The route
   returns `{as_of, blocks, degraded?}` where `blocks` went through `filterAnswerBlocks()` (manifest allowlist, band, output floor).
6. **Search keywords and library fields.** Add optional `keywords` (up to 8 strings, each up to 24 characters) to a page entry.
   Name, description and category come from the manifest (`display`, `description`, `category`); icon from the page entry.
7. **A registry the shell can read.** `GET /api/apps` (new), see "Routes".

No new record type, no new settings key, no second place list. Everything else is existing code used as it ships.

## Manifest fields (spec first, `commons/spec`)

Additive to `manifest.schema.json`, with a tag and a Home pin bump before any Home change (AGENTS.md "Pins"):

- `contributes.pages[]` keeps `id`, `icon`, `label`, `nav`, `kind`, `module`; adds `keywords` (above). `id` gains the pattern
  `^[a-z][a-z0-9-]*$` (nothing populates it today, so this tightens nothing real). `nav` is defined precisely: on the page with
  `id: "index"`, `nav: true` makes the app a library, search and pin entry (never an automatic rail icon: app-library.md keeps the
  rail for pins); on any other page, `nav: true` makes it one of the app's own sections, drawn by the shell as in-app tabs on wide
  screens and in the phone drawer (rules S1, S2). A package never draws its own chrome. Lint: the app needs one `index` page; `kind: "web"`
  stays refused; `module` names `pages/<module>.json` in the package directory.
- `contributes.data[]` (new): `{id, surface?, inputs?, refresh_s?}` as above.
- `kind: "app"` already exists in the kind enum. An app package may also be `kind: "plugin"` (Weather is one: the chat tool and the
  app are one package and one recipe, per platform principle 4). The app list reads `contributes.pages`, not `kind`.
- `spec/ui/schema.json` and the Zod mirror: binding `source` gains `"package"`, binding gains `params`, nodes `answer_blocks` and
  `picker` are added, with fixtures `spec/ui/pages/weather.json` and the ajv test. `catalog.test.ts` keeps schema and renderer
  catalog in agreement.

## Routes (hub)

All three require sign-in and apply the same gate in one function `appVisibleTo(person, manifest)`: role at or above
`min_role`, status `enabled` (smoke healthy), no missing required capability, `platforms` includes `home`, and not
`incognito: "blocked"` while Incognito is on. A package that fails the gate is 404 (hidden, not "forbidden", so existence does
not leak). Rule 0 holds: nothing here loosens an age or surface gate; a block's `min_band` and the output floor still apply per
string.

- `GET /api/apps` returns `[{package, page: "index", label, icon, description, category, keywords, sections: [{page, label, icon}], to}]`
  for the asking person, where `to` is `/apps/<package id>`. Built from `listInstalledManifests()` plus the gate. Offline safe: it
  reads disk.
- `GET /api/plugins/:id/pages/:pageId` returns the validated `page` document from `pages/<module>.json`. Validated at load and
  cached; a document that fails the spec or points a binding outside its package is refused at install, not at request time.
- `POST /api/plugins/:id/data/:dataId` body `{place?: <entity id | "current">, current?: {lat, lon, area?}}`. Resolves the place with
  `resolvePlace({person, surface})` (named entity wins, `current` only when sent, child coarsening applied), runs the recipe through
  `runPlugin()` (cache first, same as the widget route), returns `{as_of, blocks, degraded?}`. Coordinates are consumed in the call and
  never stored, logged or echoed. A failed recipe returns the typed failure kind (down, timed out, found nothing) and the page shows
  an `empty_state` in plain words with Retry; the page never fabricates data (rule 6).

## Frontend: routes and library without a rebuild

- `Routes.tsx` gets one route, `apps/*`, inside the authenticated layout, element `PackageAppPage`. It reads the splat, splits it
  into `<package id>` and `<page id>` (empty page id means `index`), fetches the page from the route above, mounts
  `PackageScopeContext`, and renders `SchemaPage`. Unknown or hidden package or page shows `NotFoundPage`. Static routes win over the
  splat, so `/apps/...` cannot shadow `/chat` or `/settings`.
- `useAppCatalog()` returns `APP_CATALOG` plus `GET /api/apps` rows, as `AppEntry` objects (`to`, `icon`, `label`, `description`,
  `category`, `keywords`). Query key `["apps"]`; the store install, uninstall, update and role-change mutations invalidate it, and it
  refetches on window focus. `filterApps` already takes an array; `favoriteApps`, `routeHeader.ts`, `useSearchCommand.ts` and
  `providers.ts` change from reading the const to taking the merged list. That is the whole "contribute to appCatalog, nav, search,
  pins" change; the static entries stay for core pages.
- Sections: `nav: true` non-index pages feed the existing selected-app sections in the drawer and the in-app tab strip, from the same
  list; `routeHeader.ts` titles the page from its label.
- Settings: the app's gear opens its `contributes.settings_area` (rule S4); Weather's saved places live there (PLACE-WEATHER-01's
  `weather.places`), so a page never needs a cross-app link.

## Pins

`ui.pinned_apps` stores `to` strings, so `/apps/weather` pins with no change to the setting or `usePinnedApps`. An app that is
uninstalled, disabled, role-hidden or Incognito-blocked is absent from the person's catalog, so `favoriteApps` already ignores the
stale route and keeps it in the stored list: a reinstall restores the pin (uninstall keeps state, PACKAGES.md). Pins are per person
and private to that person; the six-favorite sidebar limit is unchanged. In Incognito no pin is written (existing behavior).

## Offline and robot parity

- Hub page and app list: from disk, no network. Weather data: package cache serves within `stale_ok_s`; past that, and with no
  network, the data route returns the typed "down" kind and the page shows its offline `empty_state` (the manifest says
  `offline: "unavailable"`, so this is the stated behavior, not a failure to hide).
- Robot: complete without a hub (principle 2). The robot's own package host serves the same three routes from its local copy of the
  package and the same page document (`platforms` must include `bot`; the app list on the robot filters by platform). A robot with a
  screen renders `answer_blocks` through the same schema pages the DSI already uses (bot dev.md, "the shell served standalone"); a
  robot with no screen says the block's `alt`. The robot slice is separate and owned by `bot`; nothing in Home waits on it.
- Go renders the same page document natively; `answer_blocks` and `picker` are the only two new nodes it must implement, and
  `catalog.test.ts` is the agreement test.

## Role and age gates (summary)

Role: `min_role` of the package, the single definition (Weather is `child`, so everyone). Age: unchanged paths, never a page-level
setting: `resolvePlace` coarsens for a child, `filterAnswerBlocks` applies `min_band` and the output floor, and a package a minor
may not use is hidden by `min_role` and the household's capability allocation, not by the page. The page cannot ask for anything a
tool call could not.
