## The promise

Ask the house how the house works, and get an answer from the pages that shipped with your copy of Home, on your own hardware, with no account and no outside request. If the pages do not cover it, the answer says so instead of guessing. A child gets kid wording and never sees admin content.

## The two things

Their names stay apart because they are different packages with different jobs.

| Name | Kind | Job | Screen |
|---|---|---|---|
| Help knowledge | `plugin`, id `help-knowledge`, in `backend/packages/help-knowledge/` (beside `weather`) | Searches the bundled help docs for the person asking. Returns page sections with titles, page links and the audience tier. Holds all answer-source logic. | None |
| Help | `app`, id `help` | The screen: browse, search, Explain this, Ask a question, past help chats. Calls Help knowledge for every answer. Holds no answer logic. | Opens from the profile menu (App shell S2) |

HELP-AI-01's `help` bundled package and `HelpPage.tsx` are retired as names. If the app-package contract is not ready (open point 1), the Help screen ships first as a first-party shell page with the same route and the same API calls, and moves to a package when the contract lands. No second copy of any logic exists in either case.

### How Help knowledge is reached: a scope, not a new tool

`websearch` is the one lookup tool. Its `scope` argument is `reference` or `web` (or omitted), handled by `federatedLookup` in `backend/src/lib/retrieval/lookup.ts`. Help knowledge adds one value, `help`, to that enum. Reasons:

- The 8B model chooses badly among many tools (dev.md PHRASE-02, DOC-TOOL-01, knowledge-sources note). Rule 1 caps the base set at ten and conditional tools at 16. A scope value costs no tool slot.
- The model decides when to use it (rule 1). No word rule or router. The tool description gains one sentence, "scope `help` for questions about how MaiPai Home itself works", and the bench in the measurement plan proves the 8B picks it correctly.
- The `help` scope searches only the bundled help index. It never goes online and never falls through to `web`.

Spec first (org principle on shared shapes): the enum value is added in `commons/spec`, tagged, then pinned in `home` (two places per AGENTS.md pins section). The Help app calls the same lookup function server side with `scope: help`; it does not go through the model for browse or search.

## Who can see what

The asking person's role and age band decide, in code, before any text is retrieved (rule 0: age and surface gates outrank everything; rule 10: the output gate follows the person). The window the question was typed in does not matter.

| Person | Tiers searched | Wording |
|---|---|---|
| Child | `user` pages with `audience: all`, kid wording variant when one exists | Kid |
| Teen | `user` pages with `audience: all`; kid variant only where the page has no teen-safe plain version (open point 4) | Plain |
| Adult | `user` | Plain |
| Admin or owner | `user` and `admin` | Plain |
| Guest | `user` pages marked `audience: all` | Plain |

How it is enforced:

- Page frontmatter gains two fields: `tier: user | admin | dev` and `audience: all | adult | admin`. Today's `docs/user/` pages carry only `title` and `description`, so a one-time pass adds them. A page with no `tier` fails the release-time index build, so nothing unlabelled is ever indexed.
- The index stores `tier` and `audience` on every section. The query function takes the asker's role and age band from the request context, never from the model's arguments, and filters on them inside the search function. The model cannot ask for a wider scope.
- `dev` pages are never in the bundled index. They stay on GitHub and the hosted site.
- Tested by a regression test per row of the table: a child session asking for an admin-only topic gets zero admin sections and the "not covered" answer.

## The question flow

### Path A: a question asked in a regular chat

1. The person types "how do I add my daughter's phone to the family?" in an ordinary chat.
2. The turn engine runs as usual. The age and surface gates run first (rule 0).
3. The model decides this is about Home and calls `websearch` with `scope: help` (rule 1). No keyword rule decides this.
4. Help knowledge runs with the asker's role and band from request context. It returns up to five sections: title, text, page link, tier. Retrieval is keyword over page sections (see the pipeline).
5. The model writes the answer from those sections, using the style contract below. The answer cites the page link as a source chip the same way reference rows are cited today.
6. If nothing relevant is found, the tool result says "no matching help page" and the model says the docs do not cover it. A failed or empty tool never fails the answer (rule 6).
7. The exchange stays in that chat, in regular history, under that chat's normal memory and Incognito rules. Nothing is copied to a support thread.

### Path B: a question asked in the Help window

1. The person opens Help from the profile menu, taps Ask a question, and types.
2. The client sends the text to a support-chat route, with the thread id. The route resolves the person, role and band server side.
3. The route runs the same turn engine with surface `help` and a forced first retrieval: it calls the `help` scope itself before the model writes, so the window never depends on the 8B choosing to look. The model still writes the answer, under the same style contract and output gate (rule 10).
4. The streamed answer renders in the support chat. The thread is stored as described in "Storage of support threads".
5. If the engine is down, the window falls back to plain doc search (see "No-engine fallback").

Both paths call the same Help knowledge function. Path B differs only in the forced retrieval and where the thread lives.

## Answer style and the companion

The plain answer is the whole contract:

- Exact steps and the exact labels on screen, in order.
- One cited page link.
- A plain sentence when the docs do not cover the question.
- No invented menu names, no steps from the model's own memory of other products.

Companion framing (rule 14): the person's companion adds a greeting and a closing line only, through the per-request companion mechanism, never prompt prose. With companions off for that person, or Incognito (companion disabled, reusing bare mode), the plain answer is the entire answer. Companions are on for all profiles by default (SAFETY.md ruling 2026-10-14), so on most boxes both versions appear in practice.

Whether the framing hurts accuracy is measured, not assumed. See the measurement plan. The decision rule is fixed in advance: ship the framing only if step accuracy and invented-label rate with framing are within noise of the plain answer (paired 95% interval includes zero or favors framing). Otherwise ship greeting and closing only, with no framing inside the steps. Either outcome is a result, not a failure.

## Content pipeline

One markdown source, three consumers: GitHub, the hosted static site, and the in-app index.

```
docs/user/*.md        (tier: user, grade-6 wording)
docs/user/kids/*.md   (tier: user, audience: all, kid wording)
docs/admin/*.md       (tier: admin; new, pending open point 2)
docs/dev/*.md         (tier: dev; GitHub and site only, never bundled)
        |
        v
scripts/help-index-build (release time, version stamped)
        |
        +--> backend/data/help/<version>/sections.jsonl   (bundled with the release)
        +--> backend/data/help/<version>/index.json       (keyword index)
        +--> docs site build (Starlight today, Fumadocs per DOCS-GITBOOK-01)
```

- Sections are split on headings. Each section record carries page id, heading, text, page URL, `tier`, `audience`, `kid_variant_of` and the release version.
- The index is built when the release is cut, from the same checkout, and shipped inside the install. The docs a person searches are always the docs for the version they run. No download at runtime.
- Retrieval starts as keyword search over sections (BM25-style, in-process). Embeddings are added only if the measurement plan shows keyword retrieval missing answers that embeddings find, with the Orama or SQLite option measured, not assumed.
- The settings registry copy (`describeSetting`) is indexed as a second source, so a setting's label and description are defined once (org principle 4) and the docs link to it instead of restating it.
- A label-drift lint compares quoted UI labels in pages (bold or backticked button names) against the real strings in the frontend and fails the gate on a mismatch. Some existing pages already mention labels that may be stale (for example a Settings path under "AI & connections"), which is why this lint is slice 3.
- STYLE.md's page rules stay: dad test, about 7 steps and 300 words a page, no route paths, no "simply" or "just" in user pages, a "Fix a problem" front door, a "Still need help?" ending. `docs/user/chat.md` is about 2000 words today and will need splitting.
- The site generator is DOCS-GITBOOK-01's call. Help depends on it only for: pages with frontmatter, local search, and an `llms-full.txt`-style export that the index build can reuse or ignore. Rejected: DocsGPT, Onyx, sitechat, Kotaemon, Khoj, and Fumadocs' hosted Ask AI.

## Storage of support threads

- A support thread is a conversation with surface `help`. The conversation spec's surface enum (chat, overlay, pod, robot, tv, phone) gains `help`. That is an additive, spec-first change.
- "One open conversation per (person, surface)" already gives the behavior wanted: one reopenable support thread per person, resumed from Past help chats. Starting a new one closes the previous one on that surface, and it stays in the list until cleared.
- Clear removes the person's help threads and their turns for real, with a confirm.
- Exclusions, each a named regression test (a universal claim needs an inventory, VERIFICATION.md):
  - Regular chat history list and sidebar.
  - Memory judge (`backend/src/lib/memoryJudge.ts`) and episodes (`backend/src/lib/episodes.ts`): both read `conversation_turns`. I found no surface filter in either when I grepped. This is not yet confirmed as a gap, because I did not trace the call sites. The slice that adds the surface starts by listing every reader of `conversation_turns` (forgetCommand, legacyImport, memoryJudge, performance, replyConstraints, artifacts, conversationHistory, episodes, conversationTitle, dashboard) and writing the exclusion test for each.
  - Dashboard recent activity (`backend/src/lib/dashboard.ts`, line 64 reads all surfaces).
  - Global search (`backend/src/routes/search.ts`: conversations, people, apps, settings).
  - Backups and exports follow the person's normal conversation rules; help threads contain no household secrets by construction (see "Privacy row").
- Incognito: the Help window works, its thread is ephemeral (reusing the temporary-conversation behavior; `temporarySessions` today is an in-memory map in `conversationHistory.ts`), and the companion is off.
- A help question asked in a regular chat is stored only in that chat.

## No-engine fallback

When the Stack is unreachable (see the failure-shape classification: refused, dropped, hung and HTTP errors are all tested), the Help window still works as a plain doc search:

- Client-side search over a prebuilt static index shipped with the release: Pagefind (what Starlight already uses) or Orama (what Fumadocs uses). The choice follows DOCS-GITBOOK-01; the requirement is the same either way.
- The window shows the search box and results with page links, and one line saying the assistant is not available and how to bring it back (the address to open, the setting to check; error rule below).
- Verified to make no outside request: a headless test loads the Help screen with the network blocked and fails on any non-local request, and the same test runs against the built bundle.
- The Ask box is disabled, not hidden, with the reason beside it.

## Privacy row

Help knowledge declares:

- `offline: full`
- `permissions: []` (no `net:` entries)
- `incognito: unaffected` (it reads only bundled docs and holds no state)
- one `data_sources` privacy row: reads the help pages bundled with this release; nothing leaves the house.

The Help app declares `incognito: ephemeral` and `min_role: guest`. Role floors are enforced by the tier filter, not the package floor.

Logs carry no person text (rule 6a). The only counters are typed events: `help_scope_called`, `help_no_match`, `help_fallback_search`, `help_thread_cleared`, with band, never the question. The asked text and the answer live only in the thread.

Help v1 sends no household setting values to the model, only page ids and control labels. "Explain this" passes the control's label and the page id, never a value such as a name, address or token.

## Help app screens

All screens are shadcn parts or kit Elements as they ship (rules 9 and 9b). No wrapper components, no className changes to a kit part. A new part needs a `docs/design/UI-DECISIONS.md` row first; none is expected. Assistant-ui Elements draw the support chat.

1. Articles: a list of sections (Getting started, Chat, Family, Privacy, Fix a problem, and for admins, Running the box), then the page. Pages render from the bundled sections, with the page link to the hosted copy as a secondary action only when the box has internet (and the hosted site is the project's, never auto-opened).
2. Search: one box, results from the same index as the fallback. Works with the engine down.
3. Explain this: from any screen, the profile menu entry Help opens with "Explain this screen" and the screen's tour target ids (the tour system exists: `contributes.tours`, `backend/src/routes/tours.ts`, `frontend/src/shell/useTourRunner.ts`, commons `Tour.tsx`). The answer is the page for that screen plus, where a tour exists, a "Show me" button that starts the tour. The guided-tour note is stale on this point and is corrected in its own pass.
4. Ask a question: the support chat. First message carries the screen context if opened from Explain this.
5. Past help chats: the person's own help threads, newest first, reopenable.
6. Clear: "Clear my help chats" with a confirm, removing all of the person's help threads.

Per-person copy applies (S4): a child's Help uses kid wording and shows no admin sections, not an empty admin shelf. Help is global and lives in the profile menu (S2); it is not an app in the rail, and no app draws a second copy of it.

## Kid and teen wording

- Kids' pages live in `docs/user/kids/` as separate short pages, not a runtime rewrite by the model. Decided: one fact, one place for the steps; the kid page links to the same labels and the label-drift lint covers both.
- A kid page says what to do and who to ask ("ask a grown-up to...") and never describes admin screens.
- Teens get plain user pages. Where a teen-visible page is not suitable (topics only an adult controls), it is `audience: adult`. Whether teens use the kid variants is open point 4.
- A child's Help never shows admin results and never says an admin page exists. The "not covered" answer for a child suggests asking a grown-up.

## Errors that say the problem and the fix

Two parts, plain words (STYLE.md, "Error messages").

| Situation | Message |
|---|---|
| Engine down | "The assistant is not running, so I can only search the help pages. Open Settings, then Engine, to start it, or ask your admin." Admins also get the check to run on the box. |
| No page found | "The help pages do not cover that. Try different words, or ask your admin." For a child: "I could not find that. Ask a grown-up to help." |
| Index missing or version mismatch | "This box is missing its help pages. Update Home from Settings, then Updates, and they will come back." |
| Clear failed | "Your help chats could not be cleared. Try again; if it keeps happening, tell your admin." |
| Window text blocked by the output gate | The normal gate message for the person's band (rule 10), unchanged. |

Admins see the raw cause below the message; others do not (the "Context never breaks, failure copy" ruling of 2026-10-05).

## Measurement plan

All under rule 13: at least 3 repeats, paired 95% intervals, held-out split.

1. Question set: about 30 real help questions, written from the household's actual asks (setup, family, privacy, fixing things, admin tasks), with the correct steps and labels written beforehand from the pages. Split: 20 tuning, 10 held out. Include 6 questions the docs do not cover and 4 admin questions asked as a child.
2. Retrieval: for each question, is the right section in the top 5 from keyword retrieval? Report recall at 5 with a paired interval against a second retriever (embeddings) only if keyword recall is under the bar.
3. Scope choice: with `scope: help` in the tool description, how often does the resident 8B choose it for the 30 help questions, and how often does it choose it wrongly for 30 non-help questions? Counters `scope_help` beside the existing `scope_reference` and `scope_web`.
4. Framing: each question answered with and without companion greeting and closing, 3 repeats each. Score step accuracy (each required step and label present, in order) and invented labels (any label not in the pages). Paired difference with 95% interval. Decision rule as stated under "Answer style and the companion".
5. Gating: every row of "Who can see what" tested with real sessions; zero admin sections for child, teen, adult and guest.
6. Fallback: network-blocked headless load; zero outside requests.
7. Report engine build, model file and a sanitized hardware description (no hostnames).
