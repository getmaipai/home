## 1. Experience model

### What "cute" means for us

Cute is not a roast and not a cartoon that talks. For a family hub it is four things, all existing or shipped parts:

1. A name the household chose, used everywhere ("Ask Clover", "Clover is working on it"). Data on the companion record (COMP-03), not prose.
2. A face with state: a kit `Avatar` with the companion's accent and initial, plus the kit `agent-status` (working, waiting, done, failed) and `typing-indicator` Elements (CONFIRMED present in `commons/ui/src/elements`). The mascot animation (Rive, Q1) goes in the same `Avatar` slot once the companion package ships it.
3. A voice you can dial: the four companion dials in `backend/src/lib/persona.ts:60-76` (formality, complexity, engagement, filler_density), reset by "go back to default" as a Settings action. This is the Muse tone-dial beat without prompt prose.
4. Manners: it is quiet when there is nothing to say, says plainly when it is stuck (rule 6), and never asks twice for the same approval.

### First run

- **Adult (owner)**: after the existing wizard, one step "Meet your assistant" (kit `onboarding` Element): pick a name and accent, see the dials with the package defaults, one example line rendered from the dials. Then Home shows three things it can do today from installed packages (HOME-ALIVE-01g "Getting started" and 01h starters), the first being "Set a reminder for tomorrow morning". First value under five minutes on the starter model (SETUP-START-01).
- **Teen**: meets the assistant under the name the household chose, may rename it for themselves (per-person binding, COMP-04), sees the dials. No connectors offered. Their settings and memory are theirs alone (2026-09-30 ruling).
- **Child**: sees the name and face; a parent chose the companion set (COMP-04 kid-safe). No dials, no naming step, no "it will message you" promise.

### A day in the life (adult)

07:00 the morning note arrives in their own chat thread and as a notification: two lines, one suggested action, grounded only in what the hub holds (reminders due, open loops they stated, calendar if connected). Mid-day nothing: the heartbeat ran and chose silence. 17:40 "You said on Monday you would call the dentist. Want a reminder for tomorrow at 9?" (an open loop from their own words). Evening errand: "Watch this kettle and tell me if it drops under 60" becomes a price watch job; the receipt is a `schedule-card` in the thread. An approval: a connector proposes a calendar write; the `approval-card` shows the exact event; one tap; the receipt line follows; the Activity page lists it. A memory moment: "You told me Nadia dislikes mushrooms" rendered as a `memory-chips` Element that opens the memory record. A mistake: "I could not reach the calendar (timed out), so this is from your reminders only" in the model's own words, admin sees the detail indicator (rule 6).

Teen: same shape minus connectors and minus parent visibility; a teen's heartbeat is off until the teen turns it on (Q2). Child: reminders they set and parent-authored routines with fixed content at a fixed time (for example a bedtime story a parent scheduled), never a model-initiated message (Q3); approvals for anything consequential go to a parent (`approvals.requested`, audience adults, CONFIRMED `backend/src/lib/approvals.ts:83`).

## 2. System architecture

```
 person (web, robot, satellite, later Telegram)        time (scheduler tick)
        |                                                      |
        v                                                      v
  +-----------+   starts a turn as the person   +-------------------------+
  | routes/   | <------------------------------ | scheduler.ts            |
  | turn.ts   |                                 |  kind: plugin|core|turn |
  +-----------+                                 |  when: iso|every|cron   |
        |                                       +-------------------------+
        v                                                      ^
  +---------------------------- turn machine ------------------|-----------+
  | context -> policy (age, surface, do/ask/never, arg checks) |            |
  |   -> model (engine native tools, tool_choice auto)         |            |
  |   -> tool (package host | MCP client manager H2)           |            |
  |   -> output gate -> answer                                 |            |
  +----------------|-------------------------|-----------------|------------+
                   |                         |                 |
            memory store              approvals.ts        notifications.ts
         (person/household,         kind tool_action      (in_app, Telegram out)
          audiences, supersede)     + receipts                   |
                   |                         |                   |
                   +---------- Activity page (kit Elements) -----+
```

Everything proactive is a turn the scheduler starts as the owning person, so it inherits that person's band, surface, offered set, output gate and memory audiences for free. That is the whole trick, and it is why no framework is needed.

## 2b. External agent service option (owner's addition)

The question: install an agent service (OpenClaw class) outside Home, managed by the Stack like SearXNG, with Home only managing calls to it; it must be multi-user and never mix people up. Inputs: `external-agent-landscape.md` (23 projects, licences CONFIRMED by its author via `gh api`) and `external-agent-multitenancy.md` (source review of Hermes, Nanobot and OpenClaw at HEAD, paths and lines cited by its author; nothing run). Both read; findings folded in below.

### When it would beat our engine plus MCP

Only if it supplies, today, a capability our engine cannot reach through an MCP server: a working checkout, a reliable multi-step browser errand, or a connector set we would otherwise write. The landscape report finds none of the agent hosts does (REPORT: LibreChat, Khoj, Onyx have no mailbox, calendar or shopping actor built in; those arrive through MCP servers in every case). The capability that is real and outside our reach is a browser worker (Skyvern AGPL-3.0, Browser Use MIT, Stagehand MIT), and those are workers, not agent hosts.

### What an outside tool loop does to the rules

Rule 11 admits a supporting service that holds no model and speaks a standard interface. An agent service holds no weights, but it owns the four things the rules reserve to Home and the engine:

| Rule | What the outside loop does | Verdict |
|---|---|---|
| 0, 10 | Produces the final text; the per-person output gate (sentence by sentence for a child and every spoken turn) would have to run over a stream Home did not shape | Home must gate the service's stream; a service that returns whole messages fails for children by construction |
| 1 | OpenClaw has mention and command gating; Hermes has a "smart" guardian-LLM verdict in approvals (REPORT framework-hermes-nanobot.md) | a learned component in the consent path is forbidden (RULES-AND-LEARNED-COMPONENTS); a router inside the loop breaks rule 1 |
| 2, 4 | Its own system prompt, chat template handling, tool-call parsing, retries and context sizing sit between Home and llama.cpp | the engine's native features are no longer the implementation; rule 2 is broken unless the service is a pure pass-through, which none is documented to be (UNVERIFIED for LibreChat) |
| 6 | Its own failure wording and retry loops | the model would not answer in its own words from the person's band and surface |
| 14 | Persona is prompt prose in every one (SOUL.md, LibreChat agent instructions) | the companion's voice could not be a per-request adapter; a rewrite pass by our engine would double latency |
| privacy, credentials | A second credential store and a second memory store beside ours | breaks "one definition, one place"; disconnect-means-delete is unenforceable |

Conclusion on merit, before the rules: an outside loop gives adults a broader skill library sooner, at the price of a second brain, a second memory and credential store, slower turns (two services on one machine) and prose-only persona; for a family hub where Home must gate every request anyway, that trade loses. The rules reach the same answer (an outside loop that answers the person breaks 0, 2, 6 and 14), but they are not the reason. An outside service that only runs tools, with our engine deciding and answering, is an MCP server, the approved design. If the owner wants the adult-only drop-in anyway, Q7 gives the safest shape.

### Per person versus per household

Anything that holds a person's credentials, memory, sessions or browser profile runs per person or is partitioned per person with Home holding the partition key: OpenClaw's own security model is one gateway per trust boundary (REPORT: SECURITY.md lines 5-13), so an OpenClaw fleet means one Node gateway per household member, each with full-operator HTTP that Home alone may reach. A stateless worker pool (browser worker, page reader, SearXNG) runs per household with per-call credential injection and an isolated profile per person per call. A child never has a per-person instance of anything that runs tools.

### Recommended choice and fallback

Recommended: keep the architecture in section 2 (our engine, MCP client manager, scheduler, approvals) and add Stack-installed workers behind MCP for the capability gap: one browser worker (Skyvern or Browser Use, after the bench in section 7 shows a local model can drive it; adults; read-only first; purchases never), and MCP servers for mail and calendar as already listed. This gives "the most capabilities" without an outside brain.

Fallback, if the owner wants a drop-in host regardless (re-ranked on the multitenancy audit): **Hermes Agent, one standalone gateway per adult** (`gateway.standalone: true`, profile home per person, `TERMINAL_HOME_MODE=profile`, container terminal backend or terminal off, a `pre_tool_call` plugin that asks Home and fails closed on timeout; REPORT `hermes_cli/plugins.py:109, 1936-1939`). It has the only run API Home can drive and gate: `POST /v1/runs`, SSE events including `tool.started`, `tool.completed`, `approval.request`, and `POST /v1/runs/{id}/approval` (REPORT `api_server_runs.py`). Second: **OpenClaw fleet cell per adult** (the only vendor-documented tenant pattern: own container, state, credentials, token, loopback port, 2g/2cpu caps) at the cost of Docker or Podman on the household machine, a Node gateway per person, a daily update ping to turn off, plaintext OAuth tokens in cell state, and a TypeScript hook plugin for Home's veto. Third: LibreChat headless (per-user MCP and OAuth CONFIRMED, but no documented tool-call veto and a MongoDB beside SQLite). Not recommended: Nanobot (memory files shared by every session key in one instance, no approval gate, no calendar or shopping), Dify and Suna (licence), Agent Zero (single operator with shell power). Every fallback is adults only, one instance per person, Home holding the only key, child and teen never routed.

### The audit's five answers (from `external-agent-multitenancy.md`)

1. **Per-person instance shapes.** Hermes: a profile is a directory with its own memories, sessions, cron, secrets and API key, served either multiplexed in one process or as a standalone gateway per profile; the multiplexed form is "a configuration, not a person" (shared OS user, process-global MCP discovery and `TERMINAL_*`, one listener), so only standalone per person counts. Nanobot: one `--config` and `--workspace` per person, CLI-only lifecycle, Home supervises the process; a shared instance mixes memory by construction (`memory.py:77-81`). OpenClaw: a fleet cell (container) per person, or one process per `OPENCLAW_STATE_DIR`; multi-agent and multi-user modes inside one gateway are "usability features, not security boundaries" by its own docs. Idle RAM and cold start are UNVERIFIED for all three; Hermes at a 64K floor means a larger KV cache per concurrent adult.
2. **Veto and approval hooks.** Hermes: strongest (approval round trip over the run API, `pre_tool_call` blocks and fails closed, `unattended_mode: deny`); caveat that the approval prompt covers terminal commands and MCP tools rely on the hook (UNVERIFIED that it blocks them). OpenClaw: strong, `before_tool_call` and `plugin.approval.*`, but a native TypeScript plugin inside its gateway. Nanobot: none; a veto is a raising hook that aborts the run, Python in-process only. In all three, age gates and purchase or send approval stay Home's only if Home ships the hook plugin and the agent can reach nothing except through hooked tools.
3. **The 64K floor.** Hermes rejects any model served under 64K context (`model_metadata.py:272, 665-666`). On an 8B that is a KV-cache cost per adult the Stack does not plan for today; it is the main reason Hermes is a fallback, not a choice. OpenClaw and Nanobot have no floor but both warn that weak local models fail tool calls.
4. **Shell bypass.** A terminal tool defeats every hook: a model with a shell can run `himalaya send` or `curl` without passing a purchase or send tool. Hermes' own `SECURITY.md:58-60` says the only boundary against an adversarial model is OS-level isolation. So any external agent runs with the terminal off or in a container per person, never on the host as the Stack's user; Gmail and calendar in all three ride on HOME-keyed CLIs (`gog`, `gws`, `himalaya`), so HOME must be per person too.
5. **Residual cross-user risk.** Hermes standalone per person: Home must set per-person HOME, ports and keys; a past scope bug wrote one profile's memory into the default store (fixed, cited in `gateway/AGENTS.md`), so any future scope bug mixes memory silently. OpenClaw fleet: experimental, unrestricted egress by default, plaintext credentials in cell state, host trusted. Nanobot per instance: separate OS user still advised, no clean veto. None gives rule 2 pass-through (each re-parses or repairs tool calls) and only Hermes documents tool events on its stream; sentence-level gating of streamed text is UNVERIFIED for all three.

What the audit changed: the fallback order (Hermes standalone per adult first, OpenClaw fleet second, LibreChat third; Nanobot out). The recommendation (our engine plus MCP, workers behind MCP) is unchanged; the audit's own closing line says the same: never share one process across people, and run one per person with Home holding the only key if one is adopted.

Off by default for everyone: heartbeat, every connector, Telegram outbound for the note, price watch, flight search (Q12), inbound messaging.

Prompt injection and exfiltration (email, calendar, web pages, messages): structural, never a word list. (a) Tool results are data; a `write` or `physical` tool after any untrusted result in the turn asks (T4). (b) A background turn has no write or physical tools at all (no person present), so an injected instruction in a morning-note turn can at most alter wording, which passes the output gate. (c) One leg of the trifecta is removed per turn: a turn that read email or a web page cannot also send, post or call a connector with `net:` hosts beyond the one it read from (offered-set rule, computed at conversation start, T2). (d) Tool results never become memory facts (MEM-06 grounds facts in the speaker's words). (e) `ssrfGuard` (`commons/core`, hardened by NETPOLICY-01's audit) blocks private ranges and metadata hosts on every fetch. (f) The injection bench (TOOL-RESULT-TRUST-01) is a gate for the email and calendar connectors, with the bar in section 7. (g) Credentials: Home holds the app password or token as a write-only secret, injects it at process spawn, and rejects any server whose tool schema carries a credential field (tools design section 5 pattern).

Per-person isolation: every job row carries `personId` (CONFIRMED `scheduler.ts:113`, `:458-460`), every turn runs as that person, memory audiences gate what loads, and a background turn never loads another person's memory. An adult's memory never enters a child's turn (the OpenClaw "MEMORY.md only in private sessions" lesson, made structural).

Inbound channel: GATEWAY-01's PRIVACY.md verdict is required before any inbound bridge; the outbound note reuses the existing Telegram toggle and its privacy-page row (CONFIRMED `telegramChannel.ts:1-9`).

Purchases and sends: always human-approved, never for a minor, never in a background turn. V1 has no send tool and no purchase tool at all; the cart is a link.

Confirmation versus approval (decided here; the code today has a closed kind list `install_package | browse_url`, CONFIRMED `approvals.ts:28`, and refuses a person deciding their own request, CONFIRMED `approvals.ts:105`). Two paths, one audit table:
- **Confirmation**: an adult's own `write` or `physical` action inside a live turn is T4's `confirm_needed` with the `approval-card` Element; the person answers in the turn, the tool runs once, and an audit row of kind `tool_action` is written with `decidedBy` the same person and `via: confirmation`. This never goes through `decideApproval`, so the self-decide rule stays intact.
- **Approval**: a minor's consequential action, or any action proposed by a background turn (errand, watch, heartbeat) where no person was present, becomes an `approvals` row of kind `tool_action` whose requester is the errand or the minor (`requestedBy: errand:<id>` or the child's id) and whose beneficiary is the person; a parent decides for a minor, the adult decides for their own errand (the requester is the errand, not the adult, so `approvals.ts:105` holds). The row carries the exact tool, arguments and an arguments hash, so one decision covers one action and the same hash is never asked twice.
- **What resumes the work**: `decideApproval` emits an `approval.decided` event; the errand runner subscribes and enqueues a one-shot core job `errand.resume` with the approval id; that job executes the stored call once (idempotency key is the hash), posts the receipt line and the Activity row, and advances the errand from `waiting_on_you`. A denial marks the step declined, notifies the person once and leaves the errand `waiting_on_you` for a new instruction. Today approving only flips a status (`approvals.ts:97-115`); the event and the resume job are new, S.

## 8. What they do that we never will, and what we do that they cannot

Never: a roast or haggle onboarding (Poke), free-text persona files, a cloud computer or laptop control, a shared gateway for a mixed-age household, hidden memory with reset-only deletion (dots), data retained after disconnect (Instinct), a perpetual data licence, purchases driven by the model, 2FA codes read from mail, any service of ours in the data path.

What we do that they cannot: it runs in the house on the household's own machine; every person is their own trust boundary with their own band, memory, audiences and companions; a child is protected by architecture, not a setting; a teen's assistant is theirs alone; memory is a visible, editable, exportable record with provenance; a disconnect means the data is gone; the companion's voice is a measured mechanism, not a paragraph; and when the company behind the product changes its mind, nothing happens to the family (the Dot shutdown is the pitch).
