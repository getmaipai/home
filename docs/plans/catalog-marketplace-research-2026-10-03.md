### npm and PyPI provenance (short note)

- npm provenance signs build origin through Sigstore and logs it publicly; it proves where code was built, not that it is safe. 633 malicious versions reportedly carried valid provenance after a maintainer account was taken over ([VentureBeat](https://venturebeat.com/security/npm-sigstore-provenance-stolen-identity-audit-grid-2026), secondary source). npm trusted publishing (OIDC, no stored token) went GA 2025-07-31 ([GitHub changelog](https://github.blog/changelog/2025-07-31-npm-trusted-publishing-with-oidc-is-generally-available/)).
- Shai-Hulud (Sept 2025, over 200 packages; Nov 2025 wave over 700) spread by stealing long-lived tokens, so npm moved to short-lived granular tokens and trusted publishing and revoked classic tokens after 2025-11-19 ([Krebs](https://krebsonsecurity.com/2025/09/self-replicating-worm-hits-180-software-packages/), [GitHub plan](https://github.blog/security/supply-chain-security/our-plan-for-a-more-secure-npm-supply-chain/), [Zscaler](https://www.zscaler.com/blogs/security-research/shai-hulud-v2-poses-risk-npm-supply-chain)).
- PyPI Trusted Publishers plus PEP 740 Sigstore attestations (2024); about a quarter of uploads in Oct 2025 used trusted publishing; 2,000+ malware reports in 2025, 92% handled within 24 hours ([PEP 740](https://peps.python.org/pep-0740/), [PyPI blog](https://blog.pypi.org/posts/2024-11-14-pypi-now-supports-digital-attestations/), [2025 review](https://blog.pypi.org/posts/2025-12-31-pypi-2025-in-review/)).

### What to copy and what to avoid

1. Copy from Homebrew: one git repo as the index, a checksum per artifact, bottles on a free OCI or release host, deprecate then disable, and an explicit trust step for anything outside the reviewed repo.
2. Copy from the MCP Registry: namespace ownership proof, immutable versions, no semver ranges, metadata separate from binaries. Avoid its "minimal moderation" as our policy.
3. Copy from VS Code: a server-side block list that clients enforce (auto-disable). Avoid its weak publisher badge, and plan for false positives (Material Theme).
4. Copy from Obsidian: automated review on every version, a published scorecard, a paid-plugin disclosure policy. Avoid its manual queue as the only gate (7 months).
5. Copy from Home Assistant: a visible quality scale and a per-add-on privilege rating. The bundled `quality_scale.yaml` files already follow it.
6. Avoid from Open WebUI: running unreviewed code in-process with ratings as the only signal.
7. Lesson from npm, PyPI and the 2026 Obsidian attack: provenance proves origin, not intent, and a legitimate plugin can be steered by hostile data. Our signature must mean "a human reviewed this exact permission set", and tool output must stay data (RULES.md rule 7).

## 2. Minimum viable catalog

**Index format.** `getmaipai/catalog` stays the source of truth. CI generates `index.json` (and `index.json.sig`) at each release tag from `plugins/`, `skills/`, `integrations/` and so on. One entry per package version: `id`, `version`, `kind`, `tier`, `manifest_sha256`, `artifact` (URL, `sha256`, size), `min_home`, `permissions` and `data_sources` digests, `license`, `source_commit`, `deprecated`. This extends the existing `bundled-provenance.json` fields. Versions are immutable and exact (no ranges), as the MCP Registry does.

**Signing.** One catalog root key (Ed25519, minisign or equivalent) held offline by the owner, plus a CI release key it delegates to, the CI key held in a protected GitHub environment that only runs after a reviewed merge. Home ships both public keys in its source and pins them. The signature covers the index, so it states "reviewed and merged", not "who wrote it". Sigstore keyless attestation of the CI build can be added for transparency (Homebrew, npm, PyPI all use it) but is not a substitute, per the npm 633-package case above. TUF-style metadata (expiry, snapshot) is the mature pattern for rollback and freeze attacks; it was not researched in this lane (UNVERIFIED), so the MVP takes only two of its ideas: an `expires` timestamp and a monotonic `index_serial`.

**How Home verifies.** (1) Fetch `index.json` and `.sig`; check the signature against the pinned keys, `expires` not past, `index_serial` not lower than the cached one. (2) Fetch `revoked.json` (same signing, same checks). (3) For an install or update, download the artifact, check its `sha256` against the signed index, re-check `manifest_sha256`, run manifest lint. (4) Compute the permission and `data_sources` diff against the installed version; an increase needs an admin's consent, with the data-source sentence shown in plain words. (5) Install. (6) Keep the last good index on disk; offline Home keeps working and never fails a turn because the catalog is down (RULES.md rule 6 spirit).

**Where binaries live.** Recipe packages and skills are small text and live in the catalog repo, shipped as GitHub Release assets of the catalog (immutable per tag, free). Large artifacts (models, voices, wake words, MCP server packages) are never copied in: the index holds the upstream URL and a pinned `sha256` or OCI digest, and Home downloads from the upstream (download don't vendor). Where upstream is unreliable, mirror to ghcr.io (Homebrew precedent, free for public images; cost for us UNVERIFIED beyond the cited secondary source). Hosting cost target is near zero: GitHub Releases, Pages and ghcr.io.

**Kill switch.** `revoked.json` lists `id`, `versions` or a range, `reason`, `severity`, `action` (`disable` or `warn`). Home checks it on every index refresh and at every package start, disables a revoked package immediately, tells the admin, and tells nobody else a raw reason. Add a freshness rule: if the index is older than N days, Home keeps first-party packages and disables non-first-party ones for child and teen profiles (N is an owner decision, section 6).

## 3. Importing third-party tools

Common rule: the catalog stores our manifest and a pin, never the third party's code. The manifest lists permissions and `data_sources` we wrote or an assigned contributor wrote. The upstream program keeps its own licence.

**An MCP server.** Package `kind: integration` with a `runtime: mcp` block (a new field, so a spec change in `commons` first). The block pins the source by what the MCP Registry already verifies: npm package and version with integrity hash, PyPI version with file hash, OCI digest, or MCPB `fileSha256` ([package types](https://github.com/modelcontextprotocol/registry/blob/main/docs/modelcontextprotocol-io/package-types.mdx)). Home downloads, checks the checksum, then runs it as a separate supervised process over stdio, with permissions mapped to what the OS sandbox allows: `net:<host>` allowlist, `fs:<path>` scope, named secrets from the credentials center, no other environment. The manifest snapshots the server's tool names and schema hash; a changed tool list at runtime is treated as a new version that needs review (my recommendation to limit tool-poisoning updates; not drawn from a cited source). Default to local stdio servers only. Remote MCP servers send the family's data out of the house and conflict with the promise (section 6). Seed metadata from the registry's `server.json`, but treat it as untrusted input to our review, since the registry does minimal moderation.

**An OpenAPI tool.** Generate a recipe package, not code. A generator reads a pinned OpenAPI file (checksum recorded), emits one `fetch`/`pick` recipe per chosen operation in the format the 25 bundled packages already use, and a manifest whose `permissions` are the spec's server hosts (`net:api.example.com`). Credentials come from the credentials center. No new runtime is needed, so this is the cheapest import path and the one safe enough to review quickly.

**A plain script.** Runs only in the planned Deno sandbox tier, with manifest permissions translated to Deno's permission flags (Deno denies file, network and environment access unless granted; docs.deno.com not fetched, UNVERIFIED). The script is either contributed to the catalog repo (so it falls under the signed assignment) or downloaded from upstream by pinned URL and `sha256`, with the licence check run on it. A script with no `net` and no `fs` permission can be offered to a wider audience than one with them.

**AGPL and sole ownership.** The existing line is: separately run programs that talk over a protocol (stdio, HTTP) are treated as separate works, and linked or bundled code is not. The GNU GPL FAQ section on aggregation says the same in general terms ([GPL FAQ](https://www.gnu.org/licenses/gpl-faq.html#MereAggregation), from memory, not fetched: UNVERIFIED). Consequences: never import a third-party library into Home's process for a package; never copy third-party source into the catalog; a wrapper manifest is ours, the wrapped server stays upstream's. Licence check must also read the upstream's licence and record it in the index, and refuse a server whose licence forbids this use (for example the non-commercial weights case noted in docs/dev.md near line 6727). Legal confirmation needed from the owner's counsel; this document is not legal advice.

## 4. Trust tiers

| Tier | Who | Gate | Signed by | Default offered to |
|---|---|---|---|---|
| 0 First-party | MaiPai | Same CI plus owner review | Catalog root, bundled in Home | Everyone the manifest's `min_role` allows |
| 1 Reviewed community | Contributors under the signed assignment | PR, CLA, CI (manifest lint, permission diff, banned-API scan, recipe conformance, licence check, scorecard) and a human review of the permission and data-source diff | Catalog CI key | Adults. Teens and children only per the rules below |
| 2 Unreviewed | A user-added source or custom repo | None. User pins the checksum at add time | Nobody (user pin only) | Admin adults, explicit warning, off by default |

Child and teen rules (RULES.md rule 0 outranks everything, so these only tighten):
- **Child:** Tier 0 only, plus Tier 1 packages an admin approves one by one and that declare `min_role: child`, no `consequential`, no `net:` permissions beyond declared hosts, and no free-text output from a third party (page text passes the deterministic floor first, rule 7). Never Tier 2.
- **Teen:** Tier 0, and Tier 1 packages the admin enabled that declare `min_role` teen or lower. Never Tier 2.
- **Adult:** Tiers 0 and 1 by choice. Tier 2 only for an admin, on the admin's own risk, never offered in a temporary chat if the package writes.
- The offered tool set stays stable per person and surface (THIN-2F requires byte-identical across turns for the prompt-cache prefix), so tier and band filtering happens when the set is built, not per message.
- A revoked package or a stale index (section 2) removes Tier 1 for minors first.

Rationale from the evidence: Obsidian's attack and Open WebUI's CVEs both involved unreviewed code with full access; Home Assistant's rating and Homebrew's 6.0 trust step both put an explicit user decision before outside code.

## 6. Open decisions for the owner (reported, not decided)

Conflicts with our rules:
1. **Signed copyright assignment against third-party tools.** The assignment gate (sole ownership) cannot cover an upstream MCP server or script we do not own. The wrapper-and-pin design keeps their code out of the catalog, but then "every feature ships as a signed catalog package" means we sign the pin and the permissions, not the code. Confirm that is acceptable, and that contributors who refuse the assignment are simply not accepted into Tier 1.
2. **"Nothing leaves the house" against any package with `net:`.** Weather already sends a place name to Open-Meteo under `data_sources` with `opt_in`. Remote MCP servers and OpenAPI tools widen that. Decide whether remote MCP servers are allowed at all, for which tiers, and whether the privacy page must list each one.
3. **Rule 1 (the model decides) against a larger offered set.** More tools means a longer tools block and worse choices on an 8B model; THIN-2F's measurement (10, 20, 30 tools) must come first. Tier filtering must not become a word rule.
4. **Rule 11 against MCP servers that embed or call their own models.** Confirm such servers are refused or run only with Stack engines.
5. **"Download don't vendor" against availability.** If an upstream disappears, a pinned download fails. Decide whether mirroring to our ghcr.io is acceptable (it is a copy of third-party bytes, and a licence question).

Decisions only the owner can make:
6. Are commercial and paid packages supported, and does the AGPL plus sole-ownership model allow a package under a non-AGPL licence? Obsidian, VS Code and Open VSX all allow paid listings with disclosure.
7. Does Tier 2 exist at all in the first release? Recommended: no.
8. May a child ever use a Tier 1 package, or Tier 0 only? Section 4 proposes admin per-package approval.
9. The stale-index window N, and what a child's profile does when the catalog is unreachable for longer.
10. Key custody: who holds the offline root key and the CI key, and how rotation works.
11. Review capacity: Obsidian's 7-month queue shows what an unstaffed manual gate does. Who reviews Tier 1 permission diffs, and at what service level?
12. Whether to seed discovery from the official MCP Registry (preview, "minimal-to-no moderation") or from curated lists only.
13. Whether the runtime for MCP servers (Node, uv, Deno) may be installed by the Stack on the owner's machine, and which.
14. Legal review of the aggregation line in section 3 before any MCP wrapper ships.

Not verified, summarized: all primary vendor docs listed in the reading notes; GA status of the MCP Registry after late 2025; whether Obsidian still takes community-plugins.json PRs after the May 2026 hub; whether Homebrew attestation verification is now default; kill-list behaviour for Open VSX; and everything in `getmaipai/.github` and `getmaipai/catalog`.
