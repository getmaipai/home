## 1. Owner decisions (2026-11-06, final)

1. Keep Lingui and finish it.
2. Languages first: `en-US`, `en-GB`, Spanish (`es`).
3. Each person picks their language in Profile. `household.locale` is the default for new people and for the sign-in screen.
4. Catalogs are produced by the hub's own model through a repo script, then reviewed. Nothing leaves the home.
5. Backend strings that reach the screen get the same treatment, as a second slice.
6. A lint fails on a new hardcoded string.

Decisions added by the coordinator after the architect's verdict (2026-11-07): the household reviews the Spanish; `needs-review` flags
may ship on adult lines only (section 5 lists the lines that may not); Spanish is neutral international Spanish with informal "tu"; the
sign-in picker does not show each person's language; the model is told the person's language only for adults, and only in its own later
slice, C1 (section 13).

## 3. The decision in one paragraph

One catalog set, per locale, in Home. The English source text is the message id (as the two existing entries already do), written with
Lingui's runtime API (no macros; Vite 8 with `@vitejs/plugin-react` 6 has no Babel, the 2026-09 outage in `i18n.test.tsx`). A codemod
rewrites the existing strings mechanically so Codex slices need no judgment on ids. Catalogs load lazily per locale. A person's
language is `person.locale`, falling back to `household.locale`; the sign-in page uses the household value. The hub's own model
fills in untranslated entries through one repo script and marks them `needs-review`. A baseline-and-allowlist lint (`lint:i18n`) stops
new hardcoded strings. Server-sent copy that reaches the web app is sent as a message id plus values and translated by the client from
the same catalogs; the few channels with no client (Telegram, Bark, robot speech) render on the server from those same catalogs.

## 4. The setting: `person.locale`

- Key `person.locale`, scope `person`, selector `select`, options `["household", "en-US", "en-GB", "es"]`, default `"household"`
  (label "Language", option label for `household` is "Same as the home"). Declared in `backend/src/settings/uiKeys.ts` beside the other
  person display keys; `lives_in` is the Profile card (RULES S4: it is data in the spec/areas shape, drawn by the kit `SettingsShell`,
  never a page layout), `honoured_by: ["home", "bot"]`.
- `household.locale` (`coreKeys.ts`) gains the option `es`. Its label stays "Language and region", help reworded to "The default
  language for new people and the sign-in screen, and how dates, times and units show for them."
- The list of supported locales is declared once, in a new `backend/src/lib/supportedLocales.ts` (no imports). `coreKeys.ts` (both keys),
  `frontend/src/i18n.ts` and `frontend/lingui.config.ts` import it. This removes the three copies the scaffold comment admits to.
- One resolver, `resolveLocale(personId | null)` in `backend/src/lib/locale.ts`: the person's value if it is a real locale, else
  `household.locale`, else `en-US`. It is read where `household.locale` is read today: `turnMachine/nodes/context.ts` lines 422 and 454
  (the date text and episode formatter in the model's prompt: the speaking person's locale for adults only, the household value for every other turn, see the last bullet of this list), `lib/alarms.ts`, notification
  rendering, and the front end through the settings API (`getSettingValueForPerson` for system operations, `getPersonSettingValue` for
  the person's own read). No other code reads either key directly; a test greps for it.
- Existing people have no row, so they follow the household with no migration. "Default for new people" means exactly that: a new
  person has no row and follows the household until they choose. Changing the household value moves everyone who never chose.
- Teen and child profiles can set their own language (it makes no content, so the age gates of rule 0 do not apply, same ruling as the
  stems feature). A parent does not see it as a restriction. It is a person-private setting.
- Not done by this setting, and not done by F0 to F6 or B1 and B2: the model's reply language. The model answers in the language the
  person writes (its own decision, rule 1), and F0 adds no language line to any prompt. The one exception is the separate slice C1
  (section 13): a fixed language line for adult turns only. Child, teen, robot and shared-surface turns get no language line until a
  spec-first slice adds Spanish to the safety classifier (plain English string matching in `@maipai/spec/safety/ts/classifier.ts` and
  `floors.v1.json`) and measures it, because the child floor (rules 0 and 10) is English-only today and a Spanish child turn would not be
  screened as an English one is. Until then the date text in the prompt (`context.ts`) keeps today's household-locale behaviour for
  those turns; only adult turns read the person's locale for it.
- Machine-translated note. When the person picks `es` or `en-GB`, the Language card shows one line, copy on the `person.locale` key
  drawn through `describeSetting` (RULES S4 and S5): not a hand-made Alert, not a page-written sentence. Wording: "Some of this was
  translated by your home's own AI and may read oddly. If something is wrong, tell the person who runs your home." Where a chat
  feedback dialog or the LOG-PRIVACY-01c problem report is reachable for that person, the line points to it instead of "tell the
  person who runs your home". Nothing leaves the home either way, and no link points to a service outside it.

Sign-in, before a person is known: the page reads one unauthenticated `GET /api/locale` returning `{ locale }` (the household value, or
`en-US` when no household exists yet). It carries nothing else. Sign-in starts in that language. After sign-in the shell activates the
person's own. The sign-in picker does not show or switch to each person's language (decided; it would put a per-person value on a
public route).

## 5. Provider, loading and fallback chains

`frontend/src/i18n.ts` becomes a small module with these parts:

1. `en-US` is imported eagerly (source locale, always present, so nothing renders blank and the sign-in page never waits).
2. Every other catalog is a dynamic import, one chunk per locale file: `import(`./locales/${locale}/messages.po`)` (the Lingui Vite
   plugin compiles on import). Three real catalogs of roughly 3,000 entries is the size where this pays off (rough estimate, about 150 KB
   source each; measured in slice F0).
3. `activateLocale(locale, mode)` is async: it loads the chain's files, calls `i18n.load(id, messages)` for each, then
   `i18n.activate(id)`. Until the load resolves the current language stays up, so a switch never shows keys. A failed load keeps the
   current language and logs once (rule 6 in spirit: translation trouble never breaks the screen).
4. Who calls it: `useHouseholdLocale` is replaced by `usePersonLocale(person)`, run in `App.tsx` once the person is known and again when
   `person.locale` changes. It reads the person's resolved value through the settings API. Signed out, it calls `activateLocale` with
   the `GET /api/locale` value.
5. Chains are declared in `lingui.config.ts` `fallbackLocales` and mirrored by the loader (one table in `supportedLocales.ts`):
   - `en-GB` -> `en-US`. The `en-GB` file holds only entries whose spelling or wording differs (colour, organise, "Mum"). An empty
     `msgstr` falls through, so no copy is made (principle 1).
   - `es` -> `en-US`. Entries not yet translated show in English, never as ids.
   - KID-MODE-04: `<locale>-x-child` and `<locale>-x-teen`. Chain `en-US-x-child` -> `en-US`; `en-GB-x-child` -> `en-GB` -> `en-US`;
     `es-x-child` -> `es` -> `en-US`. The mode comes from `data-mode`, as KID-MODE-04 already says: the loader activates
     `<locale>-x-<mode>` and loads that chain.
   - Safety of the chain: the child and teen files hold only the override ids of the design record's section 5.3 table (a fixed, small
     set). A locale is offered to a child or teen profile only when its `-x-child` file covers 100 percent of the `en-US-x-child` ids;
     the KID-MODE-04 coverage lint is extended to enforce it. Without that, a Spanish child could fall through to adult Spanish wording
     for a line that exists because the adult wording is wrong for a child (rule 0).
   - The KID-MODE-04 reading-level lint scores English only (`text-readability`). Spanish child and teen entries cannot be scored, so
     they are never auto-accepted. `needs-review` flags may ship on adult lines only (owner decision). `check.sh --pre` fails on a
     `needs-review` flag in any of: (a) a `-x-child` or `-x-teen` file; (b) fixed spoken clip lines and robot lines (B1); (c) the
     SEARCH-DOWN-EMPTY-01 line; (d) crisis, consent and refusal copy; (e) any `es` entry that the KID-MODE-04 coverage lint renders on a
     child or teen route (the lint already renders every route as child against the seeded household; it now also lists every
     `es` id seen there). The household clears these by reviewing them (`--accept`, section 7). Until every such line is reviewed,
     `es` is not offered to child and teen profiles: the `person.locale` select hides the option for those profiles and the resolver
     treats a stored `es` on a child or teen as the household value.
6. Catalog files: `frontend/src/locales/<locale>/messages.po`, one per locale, plus the KID-MODE-04 `-x-` files. Kit strings (K slices)
   arrive as the kit's own catalogs, `@maipai/ui/locales/<locale>/messages.po`, merged at load: `i18n.load(locale, { ...kit, ...home })`.
   Kit ids are prefixed `ui.` so a Home string can never shadow one.
7. Kit access to the active language: kit components use `useLingui()` from `@lingui/react` against the `I18nProvider` Home already
   mounts, and list `@lingui/core` and `@lingui/react` as peer dependencies of `@maipai/ui`. No second i18n singleton. A kit string's
   `message` is its English default, so the kit still renders in English with no provider (its own showcase).

## 6. Extraction workflow

- Authoring (no macros): `<Trans id="Save changes" message="Save changes" />` in JSX; `i18n._({ id: "Saved {name}", message: "Saved
  {name}", values: { name } })` outside it; ICU `{count, plural, one {# item} other {# items}}` for counts; placeholders for every
  dynamic part (never concatenate translated pieces). Id equals the English text. When two meanings share a word, the id gets a
  suffix in parentheses (`Order (noun)`), written by hand.
- `bun run i18n:extract` runs `lingui extract --clean` for all locales. It adds new ids to every `.po` with an empty `msgstr` (and, for
  `en-US`, `msgstr` equals `msgid`), and removes ids no source references. The `.po` files are committed.
- `bun run i18n:codemod -- <path>` (new, `scripts/i18n-codemod.ts`, built on the same AST walk as the lint) rewrites JSX text and string
  props in the files given into `<Trans>` or `i18n._` with id equal to text, keeps JSX children valid, and leaves a `// i18n: manual`
  marker where it cannot (interpolated text, rich text with elements, which become Lingui `<Trans>` with numbered components). Codex
  or the local lane runs it, then fixes markers by hand and reviews the diff. This is what makes 2,500 strings a handful of runs.
- `bun run i18n:check` (part of `lint:i18n`): extraction is clean (no id in source missing from `en-US`, no stale id), every
  placeholder set in an `es` or `en-GB` message equals the source's, no `msgstr` contains U+2014.
- Setting copy is extracted differently, because it lives in the spec and the registry, not in source (section 10).
- Flag format: a `.po` message the model wrote carries `#, needs-review`. Slice F0 starts with a failing test proving the flag survives
  `lingui extract` round trips; if the Lingui formatter drops unknown flags, the marker is a translator comment (`# needs-review`)
  instead, and nothing else in this note changes.

## 7. The translation script

`scripts/translate-catalog.ts`, run as `bun scripts/translate-catalog.ts --locale es [--file <glob>] [--max-batches N] [--dry-run]`.

1. Reads the `.po` files for the locale and collects entries with an empty `msgstr` (and `needs-review` entries only with `--redo`).
   For `en-GB` it sends only entries the model thinks differ; see rule 3.
2. Groups by source file reference: one batch per source file (owner's instruction), split only when a file's batch passes about 150
   strings or 6,000 tokens, so a batch fits the chat model's real window with its glossary (rule 4: window is the model's real context).
3. Sends each batch to the Stack's chat role (`POST /v1/chat/completions` on the local Stack, the role request shape in
   `backend/src/lib/stack/contract.ts`; the Stack URL from the same config the hub uses). The script checks `/stack/v1` health first and
   refuses unless chat is `ready` (chat outranks everything on the resource order, so a bulk run never starves a family's chat); it
   runs batches one at a time and stops on the first "not ready". Nothing leaves the home (PRIVACY.md): the only host is the Stack.
4. Prompt, built from files, not prose in code: the glossary `frontend/src/locales/glossary.json` (term -> per-locale term; brand and
   product names stay as they are: MaiPai, Home, Stack, persona names from the roster; product words such as Companion, Household,
   Repairs, Library have fixed Spanish terms the owner can edit), the style rules (STYLE.md voice: plain words, the dad test, short
   sentences; every error line says what went wrong then what to do; no em dashes; no exclamation points), the placeholder rule
   (keep every `{name}`, ICU plural and tag exactly), a one-line context for each entry (file path, the element it sits in), and the
   target dialect. Spanish: neutral international Spanish, informal "tu" form, no "vosotros", no regional slang; recorded as a default the
   owner can change in the glossary header. `en-GB`: spelling and vocabulary only, never rewrite meaning.
5. Output is JSON `{ id, msgstr }[]`, validated: same placeholder set, same ICU shape, no U+2014, length within 3x of the source,
   no leftover English where the glossary says translate. Failing entries are retried once alone, then left empty (they show in
   English, the safe fallback) and listed.
6. Writes the `.po` with `#, needs-review` on every entry it filled. A re-run never overwrites an entry without that flag (a
   reviewed entry is final).
7. Review list: `--review` writes `data-scratch/i18n-review/<locale>.md` (git-ignored): per entry the English, the Spanish, a back
   translation from a second model call (so a reviewer who reads little Spanish can still spot a changed meaning), the source file and
   the glossary hits. `--accept <file|id>` clears the flag after a person has looked. `check.sh --pre` prints the count of
   `needs-review` entries per locale but fails only on the lines section 5 lists.
8. Logs counts and ids only, never the strings of anything personal (there are none; catalogs are product copy), and it makes no
   network call outside the Stack (a unit test stubs `fetch` and fails on any other host).
9. Tests (a failing test first): placeholder-preserving validation, one-batch-per-file grouping, refusal when chat is not ready,
   no overwrite of a reviewed entry, flag written, no em dash accepted.

The household reviews the Spanish (owner decision). The script does not make the translation correct; it makes the review small and
visible.

## 8. The lint: `bun run lint:i18n`

A bun test in `frontend/src/dev/i18nLints.test.ts` over `i18nLints.ts`, the same house pattern as `colorLints` and `kitElementLints`
(a scanner, an allowlist JSON with a reason per entry, a shrink-only baseline JSON). Added to `package.json` as `lint:i18n` and called by
`check.sh --pre` beside COPY-LINT-01.

- Reuse first (architect condition): F0 adopts `eslint-plugin-lingui` (rule `no-unlocalized-strings`) for the JSX text and prop
  scanning, and ESLint's built-in bulk suppressions (`eslint --suppress-all`, the `eslint-suppressions.json` file, which only shrinks) as
  the baseline, unless F0 records a stated reason in its report that they do not fit (for example the rule cannot see the explicit-id
  `<Trans id message>` form, or suppressions cannot count per file). The bun-test scanner described next is the fallback and is
  built only for what the plugin cannot cover (toast and `setError` calls, object-property labels, the allowlist reasons). The
  counts in section 2 come from the AST seed and may differ from the plugin's first run; the plugin's figure becomes the baseline.
- Scanner: the AST walk from section 2, plus calls: a string literal as the first argument of `toast.*`, `setError`, `new Error` that
  is shown (errors thrown for developers keep a `// i18n: dev` marker), and `label|title|description|placeholder|emptyText|hint`
  object properties in files under `shell/`, `apps/`. Flags JSX text and the listed props outside `<Trans>` or `i18n._`.
- Never flagged: a value that is not a letters-only phrase of two or more letters (numbers, punctuation, single glyphs), anything in
  `className`, `id`, `key`, `href`, `src`, `data-*`, `type`, `name`, `value`, `variant`, `size`, `role`, `to`.
- Allowlist `frontend/src/dev/i18n-allowlist.json`: `{ file, text, reason }`. For identifiers and brand names ("MaiPai", "Stack",
  "Wi-Fi", file extensions, "OK" where the kit requires it, persona names). A reason is required.
- Baseline `frontend/src/dev/i18n-baseline.json`: today's count per file (1,968 over 178 files, or the final figure the first run
  prints). The lint fails when a file's count rises, when a file not in the baseline has any, and when a baseline count is higher
  than the real count (shrink-only: a fixed file must be removed from the baseline in the same commit). Each slice shrinks it;
  the last slice deletes the file and the lint becomes absolute.
- Also fails: a `.tsx` file imports the kit and renders a kit string prop with a literal outside the rules above; a locale in
  `supportedLocales.ts` without a catalog file; a catalog without a `Language:` header.
- Acceptance for the lint itself: fails on a planted `<button>Save</button>`, on a planted `placeholder="Search"`, on a planted
  `toast.success("Saved")`; passes on the same lines inside `<Trans id message>`, and on an allowlisted brand name; baseline
  shrink-only check fails when a count is lowered in the file but not in the JSON.

## 9. Backend strings: how a server string is localized

Recommendation: the server sends a message id plus values, and the client translates it from the same catalogs. Only channels that have
no client render on the server, from those same `.po` files.

Why this and not the person's locale on every request with `t` on the server:

- Most server-sent copy the web app shows is not rendered by the server anyway. Setting labels and help come from the registry through
  `describeSetting` in the kit, and `failureCopy.ts` is already imported by the frontend. The client already holds the catalog and the
  person's locale; adding a second place that must agree on the locale (every route, every cache key) is the larger change.
- The records are stored: notifications, repairs and issue rows persist and a person can change language afterwards. Storing finished
  English prose freezes the language at creation; storing the id and values lets the row show in the language the person has now.
- One catalog set, one extractor, one lint. Server-side `t` as the main path would need the request's locale on every handler, a catalog
  loader in the backend, and cache keys that include language.
- It keeps rule S6 intact: status copy is defined in one place (`failureCopy.ts`, `roleHealth`), and every client reads it. Translating at
  the client does not make a second copy of the readiness rule.

What changes, in order:

1. `failureCopy.ts`: every string becomes `msg({ id, message })`-shaped data (a descriptor `{ id, message }`, no runtime import so the
   "no imports" header holds). The frontend calls `i18n._(descriptor)`; the voice path and out-of-app channels call the server
   renderer. `adult` and `minor` stay as separate ids (`failure.busy.adult`, `failure.busy.minor`). Minor failure lines live only in
   `failureCopy.ts` and its catalog entries; the KID-MODE-04 `-x-child` and `-x-teen` files do not override them.
2. `notificationTypes.ts`: each template becomes an id plus a values shape. The notification row stores `{ typeId, values }` (a small
   migration: existing rows keep their finished `text` as a legacy field the UI shows as is). The bell renders the id in the viewer's
   language. Callers pass `title` as a value; a title that is itself user content or model output is not translated, a title that is
   Home's own wording (a repair title, a job name) is passed as an id.
3. API `error` strings (1,645 sites): not translated and not converted wholesale. The rule is already STYLE.md's "every error says what
   went wrong and what to do"; the web app does not print `error` text from the server, it prints copy from `failureCopy.ts` or a
   per-form message keyed by the response's `code`. Slice B2 audits which routes' `error` text a screen actually prints (grep for
   `.error`/`.message` flowing into JSX or `toast`), gives those routes a stable `code`, and adds the code -> message id table on the
   client. The rest stay English developer text.
4. Out-of-app channels (Telegram, Bark, browser alerts when the page is closed, robot speech lines): `backend/src/lib/i18nServer.ts`
   loads the same compiled catalogs with `@lingui/core`, exposes `tFor(personId, descriptor, values)`, resolves the person's locale
   with `resolveLocale`, and uses the same fallback chain. The speech normalizer then runs on the result as it already does.
5. Settings copy (labels, help, option text, reason lines): section 10.
6. Model prompts and system text stay English; they are not UI.

Advisory for B1: `spokenText.ts` turns numbers into English words, so Spanish robot and spoken lines need a locale-aware path
(a per-locale number-to-words step in the speech normalizer, or `Intl`-based) before B1 renders a single non-English spoken line.
Until it exists, spoken and robot lines stay English for every person.

## 10. Setting copy (RULES S4 and S5)

The spec's copy fields stay the single English source in `commons/spec` (`keys.json`, `areas.json`), and Home's `backend/src/settings/*.ts`
keys. Adding per-locale fields to the spec would put a second definition of every key's text in the spec for every language; instead:

- `scripts/extract-setting-copy.ts` reads the live registry (spec plus Home keys) and writes
  `frontend/src/locales/setting-copy.generated.ts`: one descriptor per `label`, `help`, option label and reason line, with ids
  `setting.<key>.label`, `.help`, `.option.<value>`, `.reason.<state>`, `message` equals the spec English. Lingui extracts it like any
  source, so the existing workflow covers about 770 spec strings plus 230 Home strings with no new format. `i18n:check` fails when the
  generated file is stale against the registry (a new key is a failing check until `bun run i18n:settings` is run).
- `describeSetting` (in the kit, commons) takes an optional translator `(descriptor) => string`, called on each copy field before the
  per-person wording (the S5 per-person rule, "Disabled for the home", "Disabled by Dad"). Home passes `i18n._`. Without it the spec
  English is used, so the kit and Bot are unchanged. This is a commons change (slice K2), tagged by the session that makes it.
- S5 holds: no page hand-writes setting help. The generated file is not hand-written copy; it is the spec's copy by id. COPY-LINT-01 still
  runs on the spec English; the reading-level lint of KID-MODE-04 runs on English only (section 5).

  Child and teen setting copy stays in the spec copy fields (the per-person variants S5 describes); the generator emits those variants

- Bot (honoured_by `bot`) does not get Spanish from this. When the robot needs it, the generated catalog moves to commons as the spec's
  own `.po` set. Not decided here.

## 11. Dates, numbers and units

- One hook `useFormat()` (`frontend/src/lib/useFormat.ts`) returns `date`, `time`, `relative`, `number`, `list` and `unit` formatters
  bound to the active locale through `Intl.DateTimeFormat`, `Intl.NumberFormat`, `Intl.RelativeTimeFormat`, `Intl.ListFormat`. Slice F6
  replaces the 84 `toLocale*`/`Intl` calls (43 with no locale argument) and the `${n} min` style string joins. Plurals go through ICU in
  the message, never `n === 1 ? "" : "s"`.
- Backend: `lib/alarms.ts`, `context.ts` and the episode formatter call `Intl` with `resolveLocale(personId)`. The time zone stays
  `time.time_zone`, a separate setting.
- Units: until a separate units setting exists, a table `unitsFor(locale)` in `supportedLocales.ts` gives `en-US` imperial and 12-hour
  clock, `en-GB` metric with miles for road distance and 24-hour clock, `es` metric and 24-hour clock. That keeps `household.locale`
  help text true ("how dates, times and units show"). A person asking for another combination is a later setting, not this design.
- Currency: none shown today (no hard-coded currency was found); `Intl.NumberFormat` with the locale when one appears.
- `es` is the bare language, not `es-ES` or `es-MX`; `Intl` gives neutral date and number forms. A regional Spanish variant is a later locale entry.

## 12. Right to left

Out of scope. None of the three languages is right to left. No RTL locale is added to `supportedLocales.ts`. New Home-owned markup in
these slices may use Tailwind logical utilities (`ms-`, `me-`, `ps-`, `pe-`) where it touches a class anyway, but no sweep is done and
nothing tests mirroring. The logical utilities never go on kit parts (rule 9). A Spanish overflow on a kit part (longer labels
in a button, tab or rail name) is fixed by a prop or variant added in `commons` (its own worktree and tag), never by a Home
`className` or wrapper.

## 14. Rules touched

- **Rule 0 (age and surface gates outrank everything):** language never changes which content a person may see. Child and teen
  copy catalogs apply on top of the person's language, and a language is not offered to a child profile until its child file covers
  the override set (section 5).
- **Rule 6 (a failed tool never fails the answer), in spirit:** a failed catalog load keeps the current language; an empty entry
  shows English; translation trouble never blocks a screen or a reply.
- **Rule 9 and the kit-Elements text inside it (kit Elements as they ship) and rule 9b:** kit strings change only in `commons` (slices K1
  and K2), never by a Home `className` or a Home wrapper; Home adds no component to translate. The new Profile "Language" card
  uses the existing settings shell and the kit select as shipped.
- **Rule 10 (delivery gate, child content floor):** translated child lines are reviewed, never auto-accepted; the gate itself is untouched.
- **Rule 11 (only our own tested Stack components run the models):** the translation script uses the Stack's chat role, nothing else.
- **Rule 1 (the model decides, not a word rule):** the lint and glossary are build-time checks on source, not a turn-time filter; no word
  list touches a chat turn. The model's reply language stays the model's decision. Slice C1 touches the chat turn (rules 1 to 5, cache
  prefix) and carries its own architect verdict; the safety classifier work for non-adult turns is spec first, in `commons`.
- **S1 and S3 (rail, widths):** the rail and phone drawer tests run in `es`; longer labels must not break the 56 px rail names.
- **S4 (every settings screen is the kit settings shell):** `person.locale` is a registry key shown by `SettingsShell`.
- **S5 (copy is per person):** setting text still comes from the spec copy fields through `describeSetting`, with a translator hook; no page
  hand-writes setting help; COPY-LINT-01 keeps running on the English.
- **S6 (system status reaches the person through the existing mechanisms):** `failureCopy.ts` stays the one table; translation
  happens at the reader, so no second status copy or surface appears.
- Non-RULES: platform principles 1 and 4 (one definition: one supported-locale list, one catalog set), org PRIVACY (no outbound), org
  STYLE (no em dashes, error lines), `docs/BACKLOG-FORMAT.md` (rows below), KID-MODE-04 and COPY-LINT-01 (extended, not replaced).
