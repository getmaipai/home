# Library revamp: a Dropbox-style files page for the household (2026-10-18)

Status: audit and design only, queued behind music (MUSIC-GEN) and the licence acknowledgement by the owner's one-thing-at-a-time
rule. Nothing here is built. Owner words (Jesse, 2026-10-18): "Our library page needs a revamp: it should look and feel like a
Dropbox where you see your items in a preview mode (you can see video thumbnail, image thumbnail), you can see full screen and
preview, you can see who it is shared with, you can see item count, sizes, total storage. You can easily delete and share and
edit. Let's make it a modern, easy to use, beautiful version of a Dropbox."

Original architect verdict (written by the author, no architect agent run), with owner-decision status updated below: **APPROVED for LIBRARY-REVAMP-01 to -13
on shipped kit parts plus five named kit additions (rule 9c, `commons` first); NEEDS-SPEC for three additive `file` fields (name,
trash envelope, audience), spec first (-03), which gates -04, -10, -11 and -12; owner rulings recorded below; only upload limits and the child Ask remain open (section 8), gating -11.** The
design touches no line of `RULES.md`. It uses S2 (the Library copies the native app Jesse named), S6 (upload progress on a job
card, failures on the destructive Alert, no new status surface), rule 9 (kit as shipped) and the existing trash (TRASH-01).

Evidence: captured 2026-10-18 on origin/main `74a2516f` (Home v0.2.21), pinned `@maipai/spec` v0.1.179 and `@maipai/ui` v0.5.268,
on a scratch Home (own data directory under the session scratchpad, port 8861, owner plus a teen and a child, no engine, no
Stack). The seed wrote 20 files (19 visible to the owner) through the same `createAttachment` path the chat uses, with the same provenance notes the picture,
video and music jobs write. Captures: [today at 1440](assets/library-2026-10-18/library-today-1440.jpg) and

(clickable; desktop and phone, dark and light, an adult and a child, loading, empty, error and uploading states).

## Owner rulings

These rulings replace the earlier choices on retention, folders, sharing and duplicate files. Source for each: Jesse, 2026-10-18.

1. **Retention and generated items (Jesse, 2026-10-18):** "I don't think we should have things from chats disappear after 90 days. Admins need to be able to configure settings about retention for each type of thing. ANYTHING GENERATED is stored by default as a generated item in the library and has its own retention settings based on total storage. Chats reference those things. Chats have their own retention, and if a file is deleted from the library, there is still the copy in the chat (we should have orphan handling but we also don't want to double storage)."
2. **Folders (Jesse, 2026-10-18):** "no folders; use filters" (recommended option chosen).
3. **Sharing (Jesse, 2026-10-18):** "share with people in the home or text". Share to household members or through the phone's own share sheet. Home sends nothing to the internet and makes no link that works outside the home.
4. **Duplicate uploads (Jesse, 2026-10-18):** "their copy stays but don't waste storage: we should be single instance storage by hash and we just delete references. When all references are gone, file is gone."

## 1. The short answer

1. **Today's Library is a five-row table of media types.** It lists every stored file as `image/png`, owner, kind. The record has
   no name, so there is nothing else to show. No thumbnail, no preview, no upload, no delete, no rename, no item count, no storage
   total. The only actions are Download and Share.
2. **Most of what Jesse asked for has data behind it already:** size, owner, kind, dates, who made it and how (the provenance
   note), who it is shared with (the `shares` pointers), per-person usage with a 20 GB default cap (`/api/storage/usage`), a poster
   for every generated video, and a 30-day household trash (TRASH-01) that lacks only a file provider.
3. **Three things do not exist and are not cosmetic:** a display name, thumbnails (the grid would download every original), and
   "kept" that holds (a nightly retention job deletes every file of an aging chat, kept songs included, so a Dropbox-style Library
   that promises permanence would lose items at day 90).
4. **The design:** the page copies Dropbox (S2): a left column of sections with a storage bar at its foot, a header with item
   count and size, a toolbar of search, filter chips, sort, grid or list, and selection; big thumbnails; a full-screen preview with
   an info panel; a Share dialog with people avatars; Delete means Trash with Undo. On a phone the left column becomes a chip row,
   actions open a bottom sheet, Upload is a button at the bottom right.
5. **Thirteen slices** (LIBRARY-REVAMP-01 to -13): the data first (one listing, kept means kept, spec, an age gate, thumbnails),
   then four kit parts, then the page in three steps, then Trash, upload and edit.
6. **Owner rulings are recorded above.** Fix BUG-LIBRARY-KEPT-01 first and BUG-LIBRARY-SHARE-CHILD-01 second. Generated items outlive their chats; no folders; sharing stays in the home or uses the device share sheet; duplicate uploads keep separate references to one stored file. Only upload limits and the child Ask remain open (section 8).

## 3. B. The design

### 3.1 Rules it follows

- **S2 (each app copies its native app).** Jesse named the app: Dropbox (he typed "dropdown"). Its layout is the target: left
  sections with storage at the foot, header with count, toolbar, large thumbnails, list view, full-screen preview, share dialog,
  deleted files. Only the rail is ours. Phone copies the Dropbox phone layout: bottom-sheet item actions, an Upload button at the
  bottom right.
- **S1.** The 56 px rail is unchanged. On a phone the sections also live in the drawer below the apps (the selected app's own
  sections); the chip row on the page is the same list, drawn from the same data.
- **Rule 9.** Kit parts as shipped, restyled by tokens. A look the kit cannot reach is a kit change in `commons` first (section 4).
- **S6.** No new status surface. Upload progress is one job's progress, so it is a card per upload (the kit `JobProgress`); a
  failed upload or load is the destructive `Alert` with the next step; storage-full is the existing refusal sentence
  (`storageRefusalMessage`). Thumbnails still being made show the kind icon, never a banner.
- **Privacy.** Home shares with people in the household. Sending by text uses the device's own share sheet; Home makes no internet link (section 3.8).

### 3.4 Sections: tabs and filters only, no folders

All files, Pictures, Videos, Songs, Documents, Shared with me, Shared by me, Trash. Each shows its count. Recently made is not a
section: the default sort is Newest, and Home's "Recently made" shelf (HOME-ALIVE-01f) links to `/files?sort=new`. Fetched
podcast and saved-video copies stay out of every section: they belong to the media apps and their own trash (`podcastCopies.ts`).
"Shared with me" lists items someone else owns that name you or the household, with "Shared by <name>" on the tile.

### 3.5 Header strip and storage

The header reads "97 items · 10.9 GB" for the current section and filters (so Pictures reads "61 items · 4.6 GB"). The storage block sits
at the foot of the left column on desktop, and is a one-line "10.9 of 20 GB" under the title on a phone that opens the same
breakdown in a sheet.

- Bar: one segment per kind (Pictures, Videos, Songs, Documents, Other) using the kit chart tokens, not the mockup's hex values,
  with the legend beside it in plain words: "Pictures 4.6 GB".
- Numbers: the person's own usage and cap from `/api/storage/usage` (their row only). With no cap set, the bar shows used bytes
  and, for an admin, the free disk space from `/api/storage`; a non-admin sees used only. Never a percentage without the bytes.
- Counting: show each person's usage by unique bytes. Plain note: "Identical files count once." Multiple references to one sha256 count once per person; household totals count those bytes once across the home.
- Trash: "Trash still holds these files for 30 days." Trash holds references, so bytes still count while that person has a reference. Dropping the last reference frees the stored bytes.
- Full: the existing sentence ("Your storage is full; delete some pictures or ask a parent for more room", plus "or raise the
  limit under Settings" for an adult). A child's wording never mentions raising the limit.
- Admin: a link "Everyone's storage" to Settings, Storage. The Library never shows another person's usage.

### 3.6 Search, filters, sort and selection

- Search: server side over derived name, type, owner name and, for made items, the prompt or song title. Debounced, `/` focuses it.
- Filters: type chips (any, pictures, videos, songs, documents), "Mine", "Shared", "Only me". Sort: Newest, Name, Size (largest
  first). All are query parameters of the one listing route and of the URL, so a link restores the view.
- Selection mode: the Select button, the corner box on any tile, or `S`. The kit `BatchBar` shows "3 selected" with Share,
  Download, Delete and Done. A refused item reports why while the others go through ("4 moved to Trash. 1 is shared with you and
  is not yours to delete.", per `UI.md` Batch actions). Download of several files is a zip streamed by the hub (a later row; v1
  downloads one file at a time and disables the bulk button above one).

### 3.7 Full-screen preview

Click or Enter on a tile opens the viewer over the page (a dialog, focus trapped, focus returned to the tile on close). The URL
becomes `/files?file=<id>` (the existing contract), so Back closes the viewer and an in-home shortcut opens it after the access check.

- Image: fitted to the screen; Zoom button, `+` and `-`, double tap and pinch on a phone, drag to pan when zoomed.
- Video and song: the kit `Player` primitive (media-chrome; Range already served; Media Session and cast slots included).
- Document: a large icon tile with Download; a PDF preview inside the viewer is a later row.
- Previous and next move through the current filtered list (arrow keys, buttons, swipe on a phone). `I` shows or hides the info
  panel, `Esc` closes, `Delete` moves to Trash with Undo.
- Top bar: Close, name, Zoom (pictures), Share, Download, Edit (pictures you own), Delete, Info. Under 640 px the labels hide and
  the targets stay 48 px; the info panel becomes a bottom sheet.
- Info panel: name, type, size, added date, owner; "How it was made" ("Made in chat with Pictures", "Sent in chat on 14 Oct", with a
  link to its chat while the chat exists); who can see it (avatars with names, "Only you", or "Everyone in the home") with Manage
  sharing; Keeping ("Kept until you delete it" or the Library removal date with a Keep button); the versions of a picture.

### 3.8 Sharing: what Share means

Share has two choices (Jesse, 2026-10-18).

1. **With people in the home.** The Share dialog lists household members with avatars and "Everyone in the home" (the `household` pointer includes people who join later). The existing routes (`POST /api/files/{id}/shares`, `DELETE /api/shares/{id}`) add or drop reference rows; no bytes are copied. Copy: "People in your home can see this. You can stop sharing at any time." A recipient may share it on inside the home (decision 6 of the storage record, unchanged); the dialog then reads "Share with others". The viewer's band gates every read, including shared items, content and thumbnails.
2. **Send by text or another app.** The device's own share sheet offers text, AirDrop or Mail. Reuse Web Share and the prepared video path (`shareClip`, already built), with Download as fallback. The person chooses the app on their device; Home hosts no public file and makes no link that works outside the home.

Tiles carry avatars, the list has a Shared with column, and Info names everyone. "Shared by me" and "Shared with me" are sections. A child never sees Share or "Shared by me" controls (section 3.14). `/files?file=<id>` remains an in-home shortcut for signed-in people who can already see the item; it grants no access.

### 3.9 Edit

- **Rename:** an owner renames any item; the dialog is a single field. Needs the `name` field (-03); until then the menu item is
  absent.
- **Edit a picture:** "Open in the picture editor" goes to the chat that made it and opens the existing editor there (the editor
  needs its conversation). When that chat is gone the item is hidden and the info panel says "Its chat was deleted, so it cannot be
  edited here." A standalone editor by file id is a separate row, not part of this design.
- **A new version:** an edit saves the next version through the existing version chain; the Library shows the newest version as the
  item, with "3 versions" in the info panel and each version openable.
- **Keep:** one button pins a Library item and sets retention to `kept` (section 3.16).
- **Not offered:** video trim, audio edit, document edit. They do not exist; the Library adds no control for something that is not
  shipped.

### 3.10 Delete and Trash

- **Delete means Trash.** One unshared item: it goes at once and a toast says "'Fox' moved to Trash. Kept 30 days." with Undo
  (6 seconds). The toast is the courtesy echo; Trash is the durable undo.
- **Shared items and batches** use the kit `DestructiveConfirm` as an inline card above the grid (not a floating dialog, per
  `UI.md`): "Delete 'Otters in a kitchen'? It is shared with everyone in the home. They lose access now. You can get it back
  from Trash for 30 days."
- **Trash section:** tiles with the days left, Restore, and Delete forever; Empty Trash on the header with the inline confirm that
  names the count. After 30 days the existing six-hour sweep drops the Trash references, and removes bytes only at zero references.
- **While trashed:** shares from that Library reference stay but the item is hidden from those recipients (access ends at once, as unshare does
  today); Restore brings it and its sharing back; the bytes still count against the person's cap.
- **One trash:** `/storage/trash` lists file rows too (the provider's kind is `file`), so the Library's Trash section and the
  household Trash page read one provider.
- **References and duplicate uploads (F12):** deleting from the Library removes that person's Library reference from the active list and holds it in Trash for 30 days. Purge drops that reference. Each owner's copy has its own reference; deleting one never deletes another person's copy. No ownership transfer is needed.
- **Chat copy:** a chat keeps an orphan-safe reference to the same content row, with enough data to open the file after the Library item is deleted. It is no second copy on disk. Content stays while any owner, chat, collection, share or Trash reference remains; bytes are removed only at zero references.
- **Who may delete:** the owner only (an admin cannot delete another adult's file, nor a child's; an admin may still unshare on a
  child's behalf, as today).

### 3.11 Upload and drag and drop

- **Entry:** the Upload button (a file picker, multiple files), dragging files anywhere on the page (a dashed overlay, "Drop to add
  to your Library"), and the phone button at the bottom right. Pasting a picture also works.
- **Route:** `POST /api/library/upload`, multipart, one file per request, sent in parallel up to 3. It creates a `file`, origin
  `sent`, retention `kept`, no conversation or turn (a fetched copy already has none: `attachments.conversation_id` is nullable),
  provenance note `library:upload`, with the file's own name saved in `name` (-03). The cap check runs first
  (`checkAttachmentCapacity`), before any byte is written.
- **Accepted:** pictures, videos, audio, PDF and office documents, plain text. Limit: 500 MB per file, shown before the upload
  starts (section 8). Pictures pass the same picture cleaning chat uploads get.
- **Progress (S6, one job's progress):** a card per upload in a tray at the bottom right (above the Upload button on a phone) using
  the kit `JobProgress` (it already takes bytes done and total, a failed state and an out-of-space line): name, percent, Cancel. A failure is the destructive `Alert` in that card with the next step ("Home is
  full. Delete some files or ask a parent for more room.", "That file type is not supported. Use a picture, video, song or
  document."), with Try again. Finished items appear at the top of the grid.
- **Child:** the button reads "Ask to add a file" and starts the kid-mode Ask (kid-mode note, section 6, Photos row: adding a
  picture from a device the child does not own asks a grown-up) until that ask lands; nothing uploads silently (section 8).

### 3.12 States, keyboard and accessibility

- **Loading:** kit `Skeleton` tiles in the grid's shape (ten), never a spinner alone. **Empty:** "Nothing here yet. Pictures, videos
  and songs you make in chat land here, along with files you upload. Drop a file anywhere on this page to add it." with Upload.
  **No matches:** "No matches. Try a different word or clear a filter." with Clear filters. **Error:** the kit destructive
  `Alert` with "Home could not load your Library. Check that Home is running, then try again." and Try again (the page already uses
  `AsyncState`). **A thumbnail that fails** shows the kind icon tile, never a broken image.
- **Keyboard:** the grid is a list with roving focus; arrows move, `Enter` opens, `Space` toggles selection when selecting, `S`
  toggles selection mode, `/` focuses search, `Delete` trashes with Undo, `Esc` leaves the viewer, the menu or selection mode. A
  tile's accessible name reads "Otters in a kitchen, video, 9.4 megabytes, shared with Marlow".
- **Targets and type:** 48 px for every control on touch (the kit `hitArea` helper; the select box and actions button stay small
  to the eye and large to the finger), body type 16 px or larger, visible focus ring, reduced motion respected (the skeleton
  shimmer stops), both themes through tokens. TV: `tv: none` (drag, sheets and hover do not exist there; the Go client builds its
  own browse later).

### 3.13 Performance

- **Server paging:** `GET /api/library?limit=60&cursor=...` with the filters as parameters, newest first by `created_at` then id.
  The page loads more on scroll (an intersection observer on a sentinel), 60 at a time. Counts come from
  `GET /api/library/summary` in one grouped query (items, bytes, per kind, trash, expiring).
- **Rendering:** tiles use `content-visibility: auto` with a fixed intrinsic size and native `loading="lazy"` and
  `decoding="async"` images. A virtualised list (`@tanstack/react-virtual`) is not in v1: it is a new dependency and needs a
  `UI-DECISIONS.md` row and a measured need. Slice -07 measures scrolling 5,000 items at 1440 and 390; only a measured drop below
  the frame budget adds the dependency.
- **Thumbnails:** `GET /api/files/{id}/thumb?w=320|640`, access checked by the same `canAccessFile`, `Cache-Control: private,
  no-cache` and `ETag: "<sha256>-<w>"`, so a revoked share is refused on the next request and an unchanged thumbnail costs one
  304 with no bytes. Generated on first request with `sharp` (31 ms at 320 px on the 12 megapixel test image above), cached as a
  derived cache file keyed by sha256 and width (`thumbs/<sha256>-<w>.webp`), never a record, never counted against a cap,
  excluded from backups, rebuilt on demand, and shown as one "Previews" line in Settings, Storage with a Clear previews button.
  Budget to confirm on real photos in -05: under 40 KB at 320 px and under 25 ms server time per warm request.
- **Backfill:** none needed; thumbnails are made when first seen. An idle-lane job may warm the newest 200 after an upgrade (the
  Stack's idle priority, so chat is not touched: ISOLATION-01 holds).
- **Original bytes:** read only when the viewer opens (Range for video and audio, already served).

### 3.15 Quotas

Per-person caps exist (default 20 GB, an admin override) and a household cap exists but is unset until the wizard sets it. The
Library shows only the person's own bar. An upload or a made file that would pass a cap is refused before a byte is written with
the existing sentence. Per-person usage counts unique bytes referenced by that person once; household usage counts each sha256 once. Trash references still count until dropped.

### 3.16 Retention, generated items and single-instance storage

Every generated picture, video and song is stored by default as a Library item of kind `generated`, owned by the person who asked. This applies to anything generated, including edits and Home-written documents. Picture, video and song remain display types. Generated items are not tied to the chat's lifetime. Chats keep references to Library content; chat retention and Library retention are separate admin settings.

Admins set retention per type: pictures, videos, songs, documents, uploads, generated and trash. Sensible defaults: keep uploads and documents until the person deletes them; keep generated items until total storage is over 90%, then warn before removing the oldest unpinned generated items of that type first. The admin can change the threshold and each type's rule. Keep/pin sets retention to `kept`; the nightly job never removes a kept item. Trash defaults to 30 days. Warn before any automatic removal, and explain the type, date and storage rule in plain words. A retained chat reference still protects the bytes when a Library retention rule drops its reference.

Use one stored file per sha256. Every owner, chat, collection and share is a reference row. The existing `attachments` table needs a content table keyed by sha256 plus a references table. Backfill from `storage_path` and `sha256`, including existing dedupe shares, without losing an uploader's copy. Give chats orphan-safe references before removing old turn links. A chat expiry drops its references only; a Library delete drops that person's references only. Remove bytes only when the reference count reaches zero.

This is the fix for F5: first make the nightly retention job honor `kept`; then make both chat deletion and retention honor references through the migration. Do not treat all generated items as pinned: generated items follow their own storage-based rules unless the person chooses Keep. Dry-run the backfill on a database copy and report counts and bytes.
