# One content filter by rating, with a top level nobody gets, and one feature access check (2026-11-16)

Status: accepted (architect APPROVED 2026-11-16, CONTENT-RATINGS-NOTE); amended the same day by the owner's ruling on roles and overrides and on never telling a person they are filtered (CONTENT-RATINGS-ROLES). Owner decisions (Jesse, 2026-11-16, in chat; spelling tidied):

- "we need to address this once and for all - we need to remove all these rules for children and teens and instead have a central filter for content - all content can go through it and have a type and a rating. sometimes that rating is given externally (ex. rating of a movie, show, explicit lyrics on a song), and sometimes we need to determine (ex. news article, image, video). sometimes we wont be able to determine and it will be unknown just like movies have not rated. then we can assign ratings to user types - ex. kids get g, teens get g, pg, pg-13, and adults simply do not go through a filter."
- "so it never affects adults in terms of performance, resource utilization, errors, etc - and only applies to the groups it should and in a fast efficient way"; "the goal is to simply protect kids without hindering others".
- "we also need some sort of access control to features but perhaps that has nothing to do with kids - ex. wife and kids cant use image gen, entire family cant use coding except dad".
- "ideally we are funneling things through a chokepoint that we can just apply these things centrally and not scattered".
- "nice thing about ratings is we can leverage external and build our own ratings systems. we can have modules ... for these things."
- On the line that nothing sexual involving a minor is ever made or shown: "that's also a rating which we need mechanisms to examine content and rate. it's just a rating that applies to everyone".
- "things like this need to be fast - we can't slow down ... the entire news app from loading front page articles to rate every individual article just in time. we have to rate things as early as possible and cache those ratings. we need a system to pull in external ratings. we need systems to perform ratings ourselves".
- On who decides: "user type (teen, adult, etc) is an easy way to assign default ratings to a user. but then an admin can tweak those ratings for an individual user - ex. tommy is a teen ... dad can go to tommy's account and set news unrated for tommy OR all unrated if he wanted"; "users are assigned to a single role that gets assigned access and ratings. an admin can add overrides per user for that access or rating or globally for all access and all ratings."
- Asked what an admin may not override, about the org safety page's line that no admin setting may weaken a child's or teen's protection: "remove that ... its those type of static rules that bloat this project. and no restrictions on the child or teen role. maybe the person has roommates and they want to put them in teen and guests in child".
- "ideally we build the system so users never realize they are filtered ... we never say the word filtered or show an error or inaccessible due to your age"; in the question box: redirect, never mention why.
- "for things like web searching, we will need a design on a reasonable ratings system."
- Answered in the question box the same day: go ahead with both systems; a ceiling by kind of person that an admin can adjust per person; the child picture protections are kept as what G means for pictures; unrated is hidden for a teen unless an admin allows it.

Evidence, the comparison with other products, the audit with file and line, and the full plan: [reports/content-ratings-and-access-review-2026-11-16.md](../reports/content-ratings-and-access-review-2026-11-16.md).

## 1. Two systems

| | Question | Applies to | Checked |
|---|---|---|---|
| Feature access | May this person use this feature at all? | Anyone, by person; age is not part of it | Once, where a feature starts |
| Content filter | May this viewer see this content? | Everyone for the top level, Prohibited; otherwise only a viewer with a ceiling | At the request, at the result, and where a list is built |

Prohibited is the top of the one rating scale: sexual content involving a minor. It is a rating like the others, found by raters like the others, and everyone's ceiling is below it. Three things make it different, and all three are today's behavior kept:
1. It is the only rating question asked about an adult's content. Nothing else in the filter runs for an adult.
2. An unrun check on an adult-only media job withholds the item (chat rule 0), and the Prohibited check that chat rules 0 and 10 require always runs, whatever another rater or a declared rating returned. For an adult the Prohibited question is asked only where those rules ask it today (request-aware screening of an adult's message, direct detection on generated media); it is not added to an adult's search, news, lists or outside titles, and an adult's discussion of the subject is not filtered.
3. Nothing lowers it: no ceiling, no admin's own rating, no grant, no setting, no rater of lower priority.

Not ratings, and unchanged: crisis handling and the crisis overlay, prompt injection, jailbreak, the credential and private-data catches, age and surface access, feature switches, quotas, technical validation, the output gate's grain (a child's and every spoken turn per sentence; a teen's admin-chosen mode), no reasoning to a minor, the band topic block and its hard lines, family stories, the adult-site host list, SafeSearch and the cleaning of fetched page text.

## 2. Ratings

One scale: G (0), PG (1), PG-13 (2), R (3), X (4), Prohibited (5), and Unrated. Outside labels map onto it (TV-Y and TV-G to G; TV-PG to PG; TV-14 to PG-13; TV-MA, a song or podcast marked explicit to R; adults-only marks to X). Every stored item and every result carries one stamp: the level, whether it was given by an outside source, declared by the feature that made it, or worked out by us, and when. The stamp may carry reasons (violence, language, scary, sexual, drugs, self-harm) so a refusal can say why. A rating is worked out once and stored. A declared rating never replaces a finished-item check: what Home makes for a child or a teen is always checked when finished.

A rating comes from a **rater**, a small unit: given one kind of content it returns a level or "unrated". Raters for one content type are tried in priority order. Outside raters read a label; our own work one out (the rules check for text, the model's look at a picture, later listening to a clip). An admin's own rating applies to one outside title, never to content Home makes; it never lowers below R an item rated R or above or carrying the sexual reason when the viewer is a child or a teen; and nothing overrides a Prohibited result. A new rater that reaches the internet needs a privacy row like any outside connection.

## 3. Roles, defaults and overrides

- Each person has one role. A role is a set of controls, not an age: an admin may put a roommate in the teen role or a guest in the child role.
- The role sets the defaults: which features the person may use, and a rating ceiling (child G, teen PG-13, adult X).
- An admin may override any access or any rating ceiling, in either direction, for one person or for the whole household, for one kind of content (news, films and shows, music, the web, pictures Home makes, and so on) or for all. Example: one teen gets unrated news, or everything unrated.
- Precedence: the person's override, then the household's override, then the role's default. This is the order chat rule 0 already uses for search defaults.
- The quality levels are access too (owner, 2026-11-16: "we should probably extend this access to the boost and max"; "kids dont need max or boost, teens dont need max"). Boost and Max, per kind of work (chat, pictures, video, music, voice), are features a role may or may not use. Defaults: the child role Standard only; the teen role Standard and Boost; the adult role Standard and Boost, with Max held by admins and given to others by an override, as today. Standard is always available and Reduced is the system's own state, so neither is an access item. An override changes any of these for one person or the household, like any other access. A level is access, not content: what a level makes is still rated against the person's ceiling. A level never changes the role's other defaults or opens a feature: thinking stays off and a model with no measured record keeps the no-tools fail-safe (chat rules 2 and 8); a level whose part is not in the person's list (rule E6) is not offered, and the job runs at the highest level that has one, never on another part.
- Only an admin, or a parent through a per-child setting a parent sets today (topic levels, `synths.real_people`), sets an override. A person may lower their own ceiling and raise it back no higher than their role and overrides give.
- Fixed for everyone, with no role, override or setting: Prohibited (section 1), and crisis handling. Not role protections and not overridable either: prompt injection, jailbreak, the credential and private-data catches, technical validation, quotas, and the per-sentence check of every spoken turn. Defaults of the child and teen roles that an override may change: the output gate's grain for those roles, no reasoning, the topic block and its hard lines, family stories, the adult-site host list, SafeSearch and the cleaning of fetched page text.
- The audience Home sends the Stack is `minor` for a person whose ceiling for that kind of content is below X.
- Unrated is over the ceiling by default for the child and teen roles, unless an override allows it. An item no rater has reached yet, and anything Home made whose check could not run, is not released to anyone whose ceiling is below X, because it is not known to be under it.
- At ceiling X the filter asks only the Prohibited question, where rule 10 asks it today, and nothing else. A household where everyone is at X runs only that.
- Below X the topic block (`topicPrompt.ts`) stays and carries the conduct line (no romantic roleplay, no encouraging dependence) as a default of the role.
- What G means for pictures Home makes: the cartoon look, no photos, no reference pictures, no real people, edits only of the person's own pictures, the child rewrite, and the finished-item check that fails closed. At PG-13: no real person outside the household and no public figure. A person whose picture ceiling an admin raised gets the higher level's behavior.
- An unknown speaker and a shared surface get what rule 0 says today. A guest's default is what MODE-GUEST-01 decides.

## 4. The choke points

1. **Feature start** (the package and tool host and the API route guard): feature access.
2. **Request** (where a generating job or a search is submitted): a request that cannot come out under the ceiling is stopped or, for a child, rewritten to a kid-friendly version, before work starts.
3. **Result** (where a reply sentence, a picture, a clip or a song is released): the finished thing is rated and compared with the ceiling; a check that cannot run withholds it.
4. **List** (where a library, a feed or search results are built): rows over the ceiling are dropped on the server.

A build check fails on a new age comparison outside the audience module, the filter, the access module and the privacy module. Today's sites are on a list that may only shrink; none is removed except by its own row. Rule E6's minor list in the Stack stays as a second check until AGE-ROUTING-REMOVE-01 is ruled on.

## 5. Rate early, store, never rate while someone waits

Nothing is rated while a person waits for a list. Stored content is rated when it arrives (a library item when added, a feed article in the background fetch, a page when fetched, a stored picture in the background queue) and the stamp is kept with the content's fingerprint and the rater's version. A list is built from stored stamps only. An item not yet rated is Unrated: a viewer whose ceiling is below X does not see it until it is rated; a viewer at X sees it at once. A rater that needs a model runs through the Stack's queue at low priority. A reply, a new picture, a clip or a song cannot be rated ahead and is checked as it is released, as today. An item not yet rated is Unrated and is shown to no viewer whose ceiling is below X until it is rated; an override that allows unrated covers only an item every rater ran on and could not rate. Results that cannot be stored first (web search rows, fetched page text) are checked as they are built, by today's floors.

## 6. Never told

A person is never told they are filtered. A list leaves out what is over the ceiling, and its counts, badges and totals are worked out after that, so they add up. A feature a person may not use is absent from menus, search and the app list, and its address answers as if there were nothing there. A direct request for something over the ceiling gets a redirect, in the model's own words, to something it can do; it does not mention age, role, rules, ratings or filtering, and it never claims the thing does not exist. No error, badge, lock or notice names a filter. When a filter removed every result, the model is told "nothing suitable", never "found nothing", and redirects. A line about a missing part or a failed step is worded as a redirect when its cause is the person's ceiling or access; a status line about the system itself still says what is happening. An Ask flow an admin chose (`synths.real_people` set to `ask`, MEDIA-KID-01) stays: it is a control the admin set, not a filter notice. An admin sees each person's role, ceilings and overrides, and household counts of what was held back that name no person and no item (rule 6a). Crisis handling is the exception and always speaks plainly. One honest limit: an attentive person will sometimes notice that something is missing; the aim is no error and no label, not deception.

## 6a. Web search

Search needs its own rating design (SEARCH-RATING-01): which signals give a page or a result a level (the engine's safe mode, site lists kept on the hub, a page's own adult label, the rules check on fetched text), what Unrated means for a result nobody labeled, and how a per-person override (news unrated, the web unrated) changes each layer. Until that note is ruled on, search keeps today's floors.

## 6b. What stays that is not a rating

Privacy (what an admin can see of a child, a teen's private settings, which memories a turn may use, memory disclosure marks); limits (daily counts and minutes, as allowances any person can have); the conduct line of section 3; the non-content protections of section 1.

## 7. Feature access

A grant is already an allow or a deny of one action for one person (`use:<package>` in the closed list). One check at feature start reads it. An admin screen sets it per person per feature. A grant may deny any feature to anyone, and allows one only within rule 0's age and surface gates. `min_role` becoming a grant check is GRANTS-01, already on the backlog. Nothing here weakens a safety protection: the grant list has no action that does, and gains none.
