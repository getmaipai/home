## 1. What was decided, and what is built

**Short answer: we did not decide against a combined view. We never decided on one.** The question was not asked, and the record
spread FileTube's cross-kind pieces to other places.

What FileTube was: one app with one bottom nav (home, feed, playlists, history, then podcasts, music, books, downloads) and a Home
whose rows span every kind: "Continue watching (all kinds, by recency), New from subscriptions, Recently added, 'More from X',
From your Liked, Watch again", plus Feed mode, a timed reel that mixes books, videos, podcasts, songs (sources record, 2.5).

What we decided (quotes from the blend note):

- Section 1: "Media is one platform layer plus five app packages, not five apps with five stores." One layer, five apps; the apps share
  one progress record, one queue and one set of collections, so the data is already combined. Only the page is not.
- Section 12, row "Home rows": "universal pattern, media rows ... one row assembler per app index built from the `continue`,
  `media-collection` and `media-source` providers; the Home page uses the same functions for its shelves". So FileTube's
  cross-kind Home became a per-app assembler plus the Home page's shelves. A cross-kind page of its own was not written down.
- Section 12, row "Resume and continue": the Home page "Pick up where you left off" shelf reads chats and media progress through
  one `continue` registry. Its budget is three rows (`CONTINUE_BUDGET`), own rows only, and the media provider leaves out tracks.
- Section 12, row "Feed mode": "media-only, later". Not built, not scheduled.
- Section 15, resolved question 1: "YouTube layout or Netflix layout?" Each app copies its native app (rule S2). The overview says
  "The one Search box finds titles in all five apps."

What is built today (code and BACKLOG, 2026-10-19):

So today there is no page that shows everything together. The data for one exists; Jesse's complaint is accurate.

## 2. The overlap, stated precisely

Two things hold media-shaped content. They answer different questions.

| | Library | Media apps (and a hub over them) |
|---|---|---|
| Record | `file` (`attachments`): bytes, owner, shares, size, name, trash | `media-item` over a file or a folder path; plus `media-progress`, `media-collection` |
| Unit | a file or folder entry: "otters.mp4, 9 MB, shared with Marlow" | a title: an episode, a song, a book, with progress, a queue place, a channel or album |
| Organized by | where it lives and who it is shared with; type chips, Newest, Mine, Shared, Trash | what to watch or hear next: Continue, New, Up next, Liked, Made at home, by kind |
| Main verbs | upload, rename, share, delete, restore, see storage | play, resume, queue, like, follow, save for offline |
| Covers | pictures, documents, audio and video as files you made, uploaded or were sent | video, show, film, song, podcast episode, book, audiobook, from scanned folders, feeds, saved links, and made items |
| Rule that joins them | one `file` record per set of bytes (single instance by hash). A `media-item.location` may point at a `file`. No second copy, ever. |

Where they overlap: only a file that is both a stored file and a playable title. Today that is a song or clip made in chat, and
tomorrow an uploaded video or song (LIBRARY-REVAMP-11). Fetched podcast and saved-video copies are already kept out of the
Library's sections (library note 3.4) because they belong to the apps.

A combined media hub would be a third view over the same records. **It does not duplicate the Library**, because it stores nothing
and offers no file management: no upload, rename, folders, storage bar, Trash, or share dialog of its own. Where it touches a
Library item it links to it ("Manage in Library" opens `/files?file=<id>`, the existing deep link). It does duplicate the Library
in one place if we are careless: a "Recently made" row that lists made items and offers Share and Delete. The rule that prevents
this: **the hub is a feed, not a manager.** Every row plays or opens; nothing in the hub changes a file.

Pictures and documents are not media-hub content at all (no progress, no queue). They stay Library-only. The hub covers the eight
`media-item` kinds, plus made songs and clips.

## 3. The three options

Recommendation on merit first (section 4 checks it against rules).

### A. A combined "Media" home app (recommended)

A catalog `app` package (id `media`, `min_role: child`, no Player of its own). One index page of rows across kinds, built from the
providers that already exist. Rows: Continue (all kinds), Up next (the person's one `queue`), New from your sources, Made at home
(the in-flight Codex shelf feed), Liked, Recently added, then a chip row (All, Videos, Shows and Films, Music, Podcasts, Books)
that narrows every row to one kind. Tapping a row plays it in its own app (`playRoute(kind, id)` in `mediaApps.ts` already maps
kind to app and page), so players, dock and Media Session stay where they are built.

## 4. Recommendation

**Option A, built thin, with option B's Search provider folded in.** The reasons, on merit:

1. It answers the ask. FileTube's value was one place to see what is new, what to continue, what is next across everything. A is that
   page; B scatters it; C gives it by tearing down working apps.
2. It adds no store and no record. The hard work (one progress record, one queue, one collection shape, the band and allowlist
   gates) is done; A is a query and a page.
3. It keeps S2: the five apps stay native-feeling; the hub is a home, like Apple's TV app Home above Movies and Shows.
4. It does not overlap Library once the rule "a feed, not a manager" holds (section 2).

Checked against the rules: S2 (an app copies its native app; the hub copies the cross-kind home pattern of FileTube's Home and of
Apple's TV app Home, and the five apps keep their own), S1 (a pinned rail entry, never automatic), rule 9 and 9b (kit nodes only, no
className, no wrapper), rule 0 and the age gates (same functions, no loosening), a failed row hides and never fails the page (every
row is `hide_when_empty`), org rule 8 (a one-line verdict per slice is in section 7), principle 1 (one definition: the hub calls the
existing data ids). Nothing conflicts with `RULES.md`. A new package that adds an app to the rail
follows APP-KIND-01 to 04 and `docs/PACKAGES.md`; Jesse's word is needed for release, not for the design.

Not recommended now: C (rewrites shipped work against S2) and B alone (does not give a place to go). B's pieces still ship:
they are inside A (slices MEDIA-HUB-03 and -04).

## 5. The "Made at home" fix and the hub

The Codex job adds "Made at home" shelves to the Music and Videos apps so chat-made songs and clips appear there. This note
does not change it. What the hub does with it:

- The hub's Made at home row reads the same source as those shelves (same function, called with all kinds). It is built after that
  job lands (MEDIA-HUB-02 depends on it), so the hub never grows a second path to made files.
- A made item that is later saved to Music (MUSIC-GEN-09) becomes a `media-item`; the hub shows it once (the item wins).
- Made items follow the Library's gates: a child sees only their own and what was shared with them; an adult-only item never
  reaches a child (LIBRARY-REVAMP-04's audience, applied by the same function).
- Row actions are Play and "Manage in Library". No Share or Delete in the hub.

## 6. Questions about gates and edge cases, answered here

- **Does the hub show chats?** No. Chats stay in Chat and on the Home page Pick up shelf.
- **Does it show pictures and documents?** No (no progress, no queue); the Library has them.
- **Kid mode:** same copy as the apps ("Keep watching"); the hub has no search box for a child beyond the household library.
- **Time budget:** metered by progress across all kinds already; the hub adds nothing to meter.
- **Offline:** `offline: "degraded"`; rows are the hub's own data, so it works with the internet off. Items not saved show "Not saved".
- **Go and TV:** the hub is a schema page, so Go renders it with the other packages (MEDIA-GO-01), one focused row at a time.

## 8. Decided by Jesse (2026-10-19)

1. Build the Media home app now: **yes**, option A, the thin "Media" app package plus the media Search provider. Jesse asked first whether it overlaps with
   Library; the answer recorded here is that Library is the file manager (folders, upload, rename, share, delete, storage, Trash) and Media is a
   watch, listen and read screen over the same records, with no store of its own and no manage actions.
2. Name: **Media**.
3. Feed mode (FileTube's timed reel): **later, as a hub page** (MEDIA-HUB-06 stays unscheduled until Jesse asks).
4. Rail: **Media joins the rail as one more icon; Music, Videos, Podcasts and Books keep theirs** (rule S1 lists every app in the rail and is not changed).
   Jesse first chose one Media icon with the four hidden, then, told that this needs a change to rule S1, chose to keep all icons now. A rail setting to
   tuck apps away is a separate design if he asks for it later.
5. Placement (Jesse, 2026-10-19: "the media app should be permanent under chat"): **Media is a permanent rail entry placed directly under Chat**, in the
   rail's fixed app block like Home, Chat, Library and Family (rule S1: the main navigation is permanent), never in More, never hidden, never reordered
   by use. Music, Videos, Podcasts and Books keep their own icons after it. The phone drawer lists the same entries in the same order. Acceptance for
   MEDIA-HUB-02: the order Home, Chat, Media, then the other apps; a child, teen and guest see Media only if the hub's band and allowlist checks allow it.
